บทที่ 5 · ภาพรวม · ราว 20 นาที

หลาย worker ช่วยกัน: partition, consumer group และ rebalance

เพิ่ม consumer แล้วระบบเร็วขึ้นได้จริง แต่มีเพดาน และมีเงื่อนไขว่างานไหนทำพร้อมกันได้ งานไหนต้องรอกัน

สิ่งที่จะได้หลังจากจบบทนี้: บอกได้ว่าตั้ง Kafka:FileImportConsumers เป็นเท่าไรแล้วจะทำงานพร้อมกันได้กี่ชิ้น อธิบายได้ว่าทำไมบางครั้งเพิ่ม consumer แล้วงานยังต้องรอกัน และเล่าได้ว่าเมื่อ consumer ตัวหนึ่งดับ งานของมันไปอยู่ที่ไหน

1. ปัญหาเกิดจากอะไร

ตอนนี้ mapping-demo ตั้ง Kafka:FileImportConsumers และ Kafka:NormalizeConsumers ไว้ที่ 1 ถ้าวางไฟล์ A กับ B ติดกัน consumer ตัวเดียวต้องทำ A ให้จบก่อน ทั้งช่วงหน่วงและช่วง import แล้วจึงเริ่ม B ได้ งานยิ่งเข้ามามาก งานท้ายแถวก็ยิ่งรอนาน

บทที่ 1 ให้คำตอบไว้แล้วคือ competing consumers (concept 03) เพิ่ม worker ให้ช่วยกันหยิบงาน แต่ใน Kafka การเพิ่ม consumer มีเงื่อนไขบางอย่างที่ต้องรู้ก่อน

2. ที่มาของ concept

เริ่มจากคำถามว่า “ถ้าเปิด consumer หลายตัว จะแบ่งงานกันอย่างไรไม่ให้ทำซ้ำ” แล้วไล่คำถามที่ตามมาทีละข้อ

  1. topic ของ Kafka ไม่ลบ message หลังทำเสร็จ (บทที่ 1) ถ้าทุกตัวอ่านแถวเดียวกัน ทุกตัวก็จะได้ message ครบทุกชิ้น แล้วจะแบ่งกันอย่างไร? แบ่ง topic เป็นหลายแถวย่อย แล้วแจกแถวย่อยให้ consumer แต่ละตัว → 13 partition
  2. Kafka รู้ได้อย่างไรว่า consumer ตัวไหนเป็นทีมเดียวกันที่ต้องแบ่งงานกัน และตัวไหนต้องการอ่านครบทุก message? ให้ consumer บอกชื่อทีมของตัวเอง → 14 consumer group
  3. message ชิ้นหนึ่งจะลง partition ไหน และงานของแถวเดียวกันจะแซงกันไหม? ให้ producer แนบ key ไปกับ message แล้วใช้ key เลือก partition → 15 message key
  4. ถ้า consumer ตัวหนึ่งดับ หรือเปิดเพิ่มกลางทาง partition ที่มันถืออยู่จะเป็นอย่างไร? Kafka แจก partition ใหม่ให้ตัวที่เหลือ → 16 rebalance

3. Concept หลัก 4 ข้อ

13

Partition: หน่วยที่ใช้แบ่งงาน

Kafka แบ่ง topic เป็น partition และให้ consumer ในทีมเดียวกันถือ partition ละหนึ่งตัวเท่านั้น [Confluent] จำนวน consumer ที่ทำงานพร้อมกันได้จริงจึงไม่เกินจำนวน partition [KafkaConsumer javadoc] ส่วน message ใน partition เดียวกันทำทีละชิ้นตามลำดับ

14

Consumer group: ทีมที่แบ่งงานกัน

consumer บอก Kafka ว่าตัวเองอยู่ group ไหนผ่าน GroupId ตัวที่อยู่ group เดียวกันจะแบ่ง partition กันและได้ message คนละชิ้น (competing consumers) ส่วนคนละ group จะได้ message ครบทุกชิ้นเหมือน publish-subscribe [KafkaConsumer javadoc]

15

Message key: กำหนดว่า message ลง partition ไหน

message ที่มี key เดียวกันจะลง partition เดียวกันเสมอ และ consumer จะอ่าน message ใน partition ตามลำดับที่เขียนเข้าไป [Kafka intro] ข้อแลกเปลี่ยนคือ key ต่างกันก็อาจได้ partition เดียวกันได้ เพราะมีแค่ 3 partition ให้เลือก

16

Rebalance: consumer เข้าหรือออก partition ก็ย้ายตาม

ทุกครั้งที่มี consumer เข้าหรือออกจาก group Kafka จะแบ่ง partition ใหม่ ถ้า consumer หยุดส่งสัญญาณเกินเวลาที่ตั้งไว้ Kafka ก็นับว่าตัวนั้นออกไปแล้วและย้าย partition ไปให้ตัวอื่น [Confluent docs] การเพิ่ม worker กลางทางจึงไม่ต้องปิดระบบ

14 Consumer groupimport ใช้ group mapping-file-import (ตั้งใน Program.cs ของ Worker) normalize ใช้ group mapping-row-normalize (ใน RowNormalizeConsumer) สอง group นี้อ่านคนละ topic และจำตำแหน่งแยกกัน
03 Competing consumersKafka:FileImportConsumers และ Kafka:NormalizeConsumers คือจำนวน consumer ต่อ topic ใน Worker หนึ่ง process แต่ละตัวมี Kafka consumer ของตัวเองและรันใน thread แยก (Task.Factory.StartNew แบบ LongRunning) ตอนนี้ตั้งไว้ที่ 1 ใน appsettings.Development.json
15 Message keyfile-import ใช้ fileJobId เป็น key ส่วน row-normalize ใช้ sourceRowId ทั้งตอน import, Retry และ Reprocess งานของแถวเดียวกันจึงอยู่ partition เดิมเสมอ
16 Rebalanceทุกครั้งที่ได้ partition ใหม่ Worker เขียน log assigned partitions จาก SetPartitionsAssignedHandler ดูได้ว่า consumer แต่ละตัวถือ partition ไหน

เพราะ import ช่วงหน่วง (Import:DelaySeconds) รออยู่ใน handler consumer ตัวนั้นจึงไม่หยิบงานอื่นระหว่างหน่วง ถ้ามี import consumer ตัวเดียว ไฟล์ B ก็ต้องรอทั้งช่วงหน่วงและช่วง import ของไฟล์ A

ลองเล่น: วางไฟล์ A กับ B ติดกัน

แถวบนตั้ง FileImportConsumers = 1 แถวล่างตั้งเป็น 3 สมมติว่า key ของ A กับ B ได้คนละ partition

เปิด Worker สอง process ก็ได้ consumer เพิ่มเหมือนกัน เพราะใช้ group เดียวกัน แต่ OutboxDispatcher จะทำงานสองตัวด้วย ทั้งสองตัวเลือกแถวที่ sent_at เป็น null โดยไม่ล็อก จึงอาจส่ง message เดียวกันซ้ำ ระบบยังถูกต้องเพราะ handler รับซ้ำได้ (บทที่ 4) เรื่อง outbox จะต่อในบทที่ 6

5. ทบทวนโดยไม่เลื่อนขึ้นไปดู

1. ตั้ง Kafka:FileImportConsumers เป็น 5 แล้ววางไฟล์ 5 ไฟล์ จะ import พร้อมกันได้มากสุดกี่ไฟล์?

  1. 3 ไฟล์ เพราะ topic มีแค่ 3 partition
  2. 5 ไฟล์ เพราะเปิด consumer ไว้ 5 ตัว
  3. 1 ไฟล์ เพราะ Worker มีแค่ process เดียว
  4. 15 ไฟล์ เพราะ 5 consumer คูณ 3 partition
partition หนึ่งมี consumer ใน group ถือได้ตัวเดียว consumer อีก 2 ตัวจึงไม่ได้ partition และอยู่เฉย ๆ ส่วน thread แยกกันอยู่แล้ว การอยู่ process เดียวจึงไม่ได้จำกัด

2. ตั้ง consumer เป็น 3 แล้ว แต่วางไฟล์ A กับ B แล้ว B ยังรอ A อยู่ดี สาเหตุที่เป็นไปได้คืออะไร?

  1. key ของ A กับ B ได้ partition เดียวกัน
  2. Kafka ส่ง message ให้ทีละ group เท่านั้น
  3. consumer ทุกตัวต้องรอ commit ของกันและกัน
  4. OutboxDispatcher ส่ง B หลัง A เสร็จเท่านั้น
key ต่างกันก็ hash ได้ partition เดียวกันได้ และใน partition เดียวกัน message ทำทีละชิ้นตามลำดับ B จึงต้องรอ A

3. ทำไม message ของ row-normalize ถึงใช้ sourceRowId เป็น key?

  1. งานของแถวเดียวกันอยู่ partition เดิม ไม่ทำซ้อนกัน
  2. ให้ทุกแถวของไฟล์เดียวกันอยู่ partition เดียวกัน
  3. ให้ Kafka ลบ message เก่าของแถวนั้นทิ้งไปเอง
  4. ให้ consumer ที่ว่างที่สุดได้แถวนั้นไปทำก่อน
key เดียวกันลง partition เดียวกันเสมอ งาน import, Retry และ Reprocess ของแถวเดียวกันจึงเรียงกันใน partition เดียว และมี consumer ทำได้ทีละชิ้น ส่วนแถวคนละแถวของไฟล์เดียวกันกระจายไปหลาย partition ได้

4. consumer ตัวหนึ่งดับขณะทำงานที่ยังไม่ commit จะเกิดอะไรขึ้นกับงานนั้น?

  1. partition ย้ายไปตัวอื่น แล้วงานนั้นทำใหม่อีกรอบ
  2. งานนั้นหายไป เพราะ consumer เจ้าของดับไปแล้ว
  3. partition หยุดรอจนกว่า consumer ตัวเดิมกลับมา
  4. Kafka ส่งงานนั้นให้ consumer ทุกตัวช่วยกันทำ
Kafka rebalance ให้ consumer ที่เหลือรับ partition ไป ตัวใหม่อ่านต่อจากจุดที่ commit ล่าสุด จึงได้งานเดิมมาทำซ้ำ ตรงกับ at-least-once ในบทที่ 4

5. ถ้าจะเพิ่มบริการใหม่ที่ต้องอ่านทุก message ใน mapping.file-import โดยไม่แย่งงานจาก import ต้องตั้ง GroupId อย่างไร?

  1. ตั้ง group ใหม่ของตัวเอง ไม่ซ้ำกับที่มีอยู่
  2. ใช้ group mapping-file-import ตัวเดิม
  3. ใช้ group mapping-row-normalize แทน
  4. ไม่ต้องตั้ง group เพราะ Kafka แจกให้ครบอยู่แล้ว
ถ้าใช้ group เดิม บริการใหม่จะกลายเป็นสมาชิกทีม import และแย่ง partition ไป ต้องเป็นคนละ group จึงจะได้ message ครบทุกชิ้นของตัวเอง

พรุ่งนี้ลองกลับมาทำอีกรอบโดยไม่อ่านเนื้อหาก่อน

6. ลองกับระบบจริง (ไม่บังคับ)

รันเดโมตาม README ไว้ก่อน ยกเว้น Worker ให้เปิดตามขั้นที่ 2

ทายก่อนลงมือ: ถ้าเปิด Worker ด้วย Kafka:FileImportConsumers=4 log assigned partitions ของ import consumer ทั้ง 4 ตัวจะออกมาหน้าตาอย่างไร

  1. ดูว่า topic มีกี่ partition: 
    docker compose exec -T kafka /opt/kafka/bin/kafka-topics.sh `
    --bootstrap-server kafka:19092 --describe --topic mapping.file-import
  2. เปิด Worker แบบ import consumer 3 ตัว และหน่วงให้นานพอเห็น: 
    dotnet run --project src/MappingDemo.Worker -- `
    Kafka:FileImportConsumers=3 `
    Import:DelaySeconds=10 `
    Demo:ImportRowDelayMs=200
    รอจน log แสดง assigned partitions ของ consumer ทั้งสามตัว
  3. วางไฟล์ A กับ B ติดกัน: 
    Copy-Item ./samples/acceptance/01-orders-a-invalid-2.csv ./input/orders/orders-a.csv
Copy-Item ./samples/acceptance/01-orders-b-valid.csv ./input/orders/orders-b.csv
  4. ดู log บรรทัด consumed mapping.file-import, partition … ว่า A กับ B ได้ partition ไหน และมี log is delaying ของทั้งสองงานห่างกันแค่ไม่กี่วินาทีหรือไม่
  5. ปิด Worker แล้วทำซ้ำด้วย Kafka:FileImportConsumers=1 เทียบว่า B เริ่มหน่วงช้ากว่าเดิมแค่ไหน
  6. ลองเปิดด้วย Kafka:FileImportConsumers=4 แล้วเทียบ log กับที่ทายไว้
