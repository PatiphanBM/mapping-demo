คิวแก้ปัญหาอะไร

เริ่มจากปัญหาที่ระบบส่งงานกับระบบทำงานเจอ แล้วไล่ดูว่าแต่ละปัญหาพาไปสู่ concept ไหนของ queue

สิ่งที่จะได้หลังจากจบบทนี้: แยกได้ว่าสถานการณ์จริงแต่ละแบบใช้ concept ไหนของ queue (decoupling, load leveling, competing consumers, publish-subscribe, at-least-once) และอธิบายได้ว่า Kafka ต่างจาก queue แบบดั้งเดิมอย่างไร ส่วนบทที่ 2 จะพาไปดูว่า mapping-demo ใช้ concept เหล่านี้อย่างไร

1. ปัญหาเกิดจากอะไร

ระบบที่มี “คนส่งงาน” กับ “คนทำงาน” มักเจอปัญหาเดียวกัน คืองานมาไม่สม่ำเสมอ แต่คนทำงานมีจำกัด เช่น ร้านกาแฟตอนแปดโมงเช้า ธนาคารวันเงินเดือนออก หรือระบบ import ที่มีคนโยนไฟล์ CSV เข้ามาพร้อมกันสิบไฟล์

ถ้าให้ API รับไฟล์แล้ว import เองในคำขอเดียวกัน ผู้ใช้ต้องรอจน import เสร็จ ถ้า import ค้าง API ก็ค้างตาม และถ้าไฟล์เข้ามาพร้อมกันมาก ๆ เครื่องก็รับไม่ไหว

2. ที่มาของ concept

ทางออกแรกคือให้งานรอในคิว แล้วให้ worker หยิบไปทำทีหลัง แต่พอทำแบบนี้ก็มีคำถามตามมาเป็นข้อ ๆ

  1. API ต้องรู้จัก worker หรือต้องรอให้ worker เปิดอยู่ไหม? API ฝากงานไว้ในคิวแล้วตอบผู้ใช้ได้เลย worker จะเปิดขึ้นมาทีหลังก็ได้ [IBM MQSeries] → 01 decoupling
  2. ถ้างานเข้ามาพร้อมกันมาก ๆ worker ต้องเร่งตามไหม? งานรอในคิวได้ worker ทำไปตามจังหวะเดิม ขอแค่โดยเฉลี่ยทำทันงานที่เข้ามา ถ้าไม่ทัน คิวจะยาวขึ้นเรื่อย ๆ → 02 load leveling
  3. ถ้าทำไม่ทันจริง ๆ จะเร่งอย่างไรโดยที่งานชิ้นเดียวไม่โดนทำสองรอบ? เปิด worker เพิ่มให้หยิบจากคิวเดียวกัน คิวส่งงานแต่ละชิ้นให้ worker แค่ตัวเดียว → 03 competing consumers
  4. ถ้าหลายระบบอยากรู้เรื่องเดียวกัน เช่น มีสมาชิกใหม่ คนส่งต้องส่งให้ทีละระบบเองไหม? ส่งครั้งเดียวแล้วให้คิวกระจายสำเนาให้ทุกระบบได้ ก่อนอื่นต้องแยกว่าอะไรเป็น “งาน” ที่ควรทำครั้งเดียว และอะไรเป็น “ข่าว” ที่ทุกระบบต้องได้ → 04 point-to-point กับ publish-subscribe
  5. ถ้า worker ดับกลางงาน งานนั้นหายไหม? ถ้า worker แจ้งคิวหลังทำเสร็จ งานไม่หาย เพราะคิวจะส่งงานที่ยังไม่ได้รับแจ้งมาให้ใหม่ ข้อเสียคืองานเดิมอาจโดนทำสองรอบ → 05 at-least-once

อีกคำถามหนึ่งแยก Kafka ออกจาก queue แบบดั้งเดิม: ถ้าอยากย้อนอ่าน message ที่ทำไปแล้ว หรือมีระบบใหม่อยากอ่านข้อมูลชุดเดิมตั้งแต่ต้น จะทำได้ไหม? queue แบบดั้งเดิมลบ message เมื่อทำเสร็จ จึงย้อนไม่ได้ ส่วน Kafka เก็บ message ไว้ตามระยะเวลาที่ตั้ง และให้ consumer แต่ละกลุ่มจำเองว่าอ่านถึงไหน [Kreps et al.]

3. Concept หลัก 5 ข้อ

IBM MQ, RabbitMQ, SQS และ Kafka ล้วนใช้ concept ชุดนี้ ต่างกันแค่วิธีทำ

01

Decoupling: แยกคนสั่งออกจากคนทำ

producer ฝากงานไว้แล้วไปทำอย่างอื่นต่อได้ทันที ไม่ต้องรอผล และไม่ต้องสนใจว่า worker เปิดอยู่หรือเปล่า

ที่มา: IBM MQSeries

02

Load leveling: ใช้คิวพักงานช่วงพีค

งานเข้าเป็นระลอก แต่ worker ทำในจังหวะคงที่ของตัวเอง คิวเป็นกันชนระหว่างสองฝั่ง [Microsoft]

ข้อควรระวัง: ถ้าโดยเฉลี่ยงานเข้าเร็วกว่าที่ทำทัน คิวจะยาวขึ้นไม่สิ้นสุด (ข้อสรุปจาก queueing theory)

03

Competing consumers: เพิ่มจำนวน worker

ทำไม่ทันก็เพิ่ม worker ให้แย่งกันหยิบงานจากคิวเดียวกัน งานแต่ละชิ้นจะมี worker ทำแค่ตัวเดียว

ที่มา: EIP, Competing Consumers

04

Point-to-point กับ Publish-subscribe

“งาน” ควรทำแค่ครั้งเดียว ส่วน “ข่าว” ควรถึงทุกฝ่ายที่สนใจ ฝ่ายละหนึ่งสำเนา

ที่มา: EIP, Point-to-Point · Publish-Subscribe

05

At-least-once: งานเดิมอาจทำซ้ำได้

worker ต้องแจ้งคิวเมื่อทำเสร็จ ถ้าดับไปก่อนแจ้ง คิวจะส่งงานชิ้นนั้นมาให้ทำอีกรอบ งานจึงไม่หาย แต่อาจทำซ้ำ worker จึงต้องออกแบบให้ทำงานเดิมซ้ำได้โดยไม่เกิดผลซ้ำ (idempotent) [Microsoft]

งานที่ลองกี่รอบก็พัง ระบบมักย้ายไปพักไว้ใน dead-letter queue จะได้ไม่ขวางงานอื่น [EIP]

4. ฝึกแยก concept จากสถานการณ์

อ่านสถานการณ์แล้วเลือก concept ที่ตรงที่สุด ลองตอบเองก่อนโดยไม่เลื่อนขึ้นไปดู

1. ร้านออนไลน์ช่วง 11.11 มีออเดอร์เข้ามามากกว่าปกติ 50 เท่าในชั่วโมงเดียว แต่ระบบตัดสต็อกยังทำงานด้วยความเร็วเท่าเดิม ออเดอร์จึงรออยู่ในคิว แล้วระบบก็ค่อย ๆ ทำจนหมดภายในคืนนั้น

  1. Load leveling: ใช้คิวพักงานช่วงพีค
  2. Competing consumers: เพิ่มจำนวน worker
  3. Publish-subscribe: ส่งสำเนาให้ทุกคน
  4. At-least-once: งานเดิมอาจทำซ้ำได้
ไม่ได้เพิ่ม worker และไม่ได้ส่งสำเนา คิวแค่รับงานที่ทะลักเข้ามาไว้ก่อน แล้วทยอยปล่อยออกในจังหวะที่ระบบปลายทางรับไหว

2. คิวงานส่งอีเมลยาวขึ้นเรื่อย ๆ ทีมจึงเปิดโปรแกรมส่งอีเมลเพิ่มอีก 3 ตัว ให้ช่วยกันหยิบงานจากคิวเดียวกัน อีเมลแต่ละฉบับส่งออกไปแค่ครั้งเดียว

  1. Competing consumers: เพิ่มจำนวน worker
  2. Publish-subscribe: ส่งสำเนาให้ทุกคน
  3. Decoupling: แยกคนสั่งออกจากคนทำ
  4. Load leveling: ใช้คิวพักงานช่วงพีค
worker หลายตัวแย่งกันหยิบงานจากคิวเดียว และงานแต่ละชิ้นมี worker ทำแค่ตัวเดียว

3. เมื่อลูกค้าสมัครสมาชิก ระบบอีเมลต้อนรับ ระบบแต้มสะสม และระบบสถิติ ต่างได้รับข่าว “มีสมาชิกใหม่” ชิ้นเดียวกัน ระบบละหนึ่งสำเนา

  1. Publish-subscribe: ส่งสำเนาให้ทุกคน
  2. Competing consumers: เพิ่มจำนวน worker
  3. At-least-once: งานเดิมอาจทำซ้ำได้
  4. Decoupling: แยกคนสั่งออกจากคนทำ
สามระบบไม่ได้แย่งงานกัน แต่ละระบบต้องได้ข่าวครบทุกชิ้น ข่าวใช้ publish-subscribe ส่วนงานที่ควรทำครั้งเดียวใช้ point-to-point

4. worker ตัดบัตรเครดิตสำเร็จ แต่เครื่องดับก่อนจะแจ้งคิวว่าเสร็จ พอเปิดเครื่องใหม่ งานเดิมก็กลับมาอีกรอบ ทีมจึงต้องเช็กก่อนว่าเคยตัดเงินรายการนี้ไปแล้วหรือยัง

  1. At-least-once: งานเดิมอาจทำซ้ำได้
  2. Load leveling: ใช้คิวพักงานช่วงพีค
  3. Decoupling: แยกคนสั่งออกจากคนทำ
  4. Publish-subscribe: ส่งสำเนาให้ทุกคน
คิวรับประกันว่างานไม่หาย แต่ไม่รับประกันว่างานไม่ซ้ำ การเช็กว่าเคยตัดเงินไปแล้วหรือยังทำให้ worker เป็น idempotent

5. เว็บอัปโหลดรูปตอบผู้ใช้ทันทีว่า “รับไฟล์แล้ว” ส่วนการย่อรูปให้อีกโปรแกรมหนึ่งทำทีหลัง ต่อให้โปรแกรมย่อรูปปิดอยู่ ผู้ใช้ก็ยังอัปโหลดได้ตามปกติ

  1. Decoupling: แยกคนสั่งออกจากคนทำ
  2. Competing consumers: เพิ่มจำนวน worker
  3. At-least-once: งานเดิมอาจทำซ้ำได้
  4. Load leveling: ใช้คิวพักงานช่วงพีค
ฝั่งรับไฟล์ไม่ต้องรอ และไม่ต้องสนใจว่าฝั่งย่อรูปเปิดอยู่หรือเปล่า

6. Kafka ต่างจาก queue แบบดั้งเดิมอย่างไร?

  1. เก็บ message ไว้ และให้ consumer จำตำแหน่งเอง
  2. ลบ message ทันทีที่ consumer ยืนยันว่าทำเสร็จ
  3. ส่ง message ให้ consumer ได้เพียงตัวเดียวเสมอ
  4. บังคับให้ producer กับ consumer ออนไลน์พร้อมกัน
เปเปอร์ Kafka ปี 2011 เขียนว่า consumer เก็บตำแหน่งที่ตัวเองอ่านถึงเอง และ Kafka ลบ message ตามระยะเวลาที่ตั้งไว้ ไม่ได้ลบเมื่อมีคนอ่าน

7. คิวของระบบหนึ่งยาวขึ้นทุกวัน ทีมเลยเพิ่มที่เก็บให้คิวรับงานได้มากขึ้น ปัญหาจะหายไหม?

  1. ไม่หาย ถ้าโดยเฉลี่ยงานเข้าเร็วกว่าที่ทำทัน งานจะค้างเพิ่มไปเรื่อย ๆ
  2. หาย เพราะคิวที่ใหญ่ขึ้นรับงานช่วงพีคได้หมด
  3. หาย เพราะคิวจะลบงานเก่าทิ้งเองเมื่อเต็ม
  4. ไม่หาย เพราะคิวที่ใหญ่ขึ้นทำให้ worker ทำงานซ้ำ
load leveling ช่วยรับงานช่วงพีคสั้น ๆ แต่ถ้าอัตรางานเข้าเฉลี่ยสูงกว่าอัตราที่ทำได้ ที่รอใหญ่แค่ไหนก็เต็มสักวัน ต้องเพิ่ม worker (concept 03) หรือทำให้งานแต่ละชิ้นเร็วขึ้น

พรุ่งนี้ลองกลับมาทำอีกรอบโดยไม่อ่านเนื้อหาก่อน

5. ทายก่อนเข้าบทที่ 2

mapping-demo ใช้ทั้ง 5 concept ลองเดาว่าแต่ละข้ออยู่ตรงไหนของโปรเจกต์ จดคำตอบไว้ แล้วไปดูเฉลยในบทที่ 2

  1. Decoupling: ใครฝากงาน ใครทำงาน?
  2. Load leveling: ถ้ามีคนโยนไฟล์เข้ามาพร้อมกัน 20 ไฟล์ จะเกิดอะไร?
  3. Competing consumers: ถ้าอยากให้ import เร็วขึ้น จะปรับค่าอะไร?
  4. Point-to-point หรือ publish-subscribe: งาน import หนึ่งไฟล์ควรทำกี่ครั้ง?
  5. At-least-once: ถ้า Worker ดับกลางงาน ระบบรับมือยังไง?

6. อธิบายด้วยคำพูดตัวเอง

พิมพ์ตอบ Claude ในแชท 2 ถึง 3 ประโยค เหมือนเล่าให้เพื่อนร่วมทีมฟังว่า queue แก้ปัญหาอะไร และ Kafka ต่างจาก queue แบบเดิมตรงไหน

Claude จะตรวจและบอกว่าตรงไหนยังคลาดเคลื่อน ถ้าตรงไหนในบทนี้ยังงง ถามในแชทได้เลย
