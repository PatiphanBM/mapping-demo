กล่องจดหมายขาออก: ทำไมไม่ส่งเข้า queue ตรง ๆ

ทุกครั้งที่ mapping-demo สร้างงาน ต้องทำสองอย่างคือบันทึกงานลงฐานข้อมูลและส่ง message ให้ Worker ถ้าอย่างหนึ่งสำเร็จแต่อีกอย่างพัง งานจะค้างหรือหายไปโดยไม่มีใครรู้

สิ่งที่จะได้หลังจากจบบทนี้: อธิบายได้ว่าทำไม File Watcher เขียนแค่ PostgreSQL แล้วให้ OutboxDispatcher ส่งเข้า Kafka ทีหลัง และเล่าได้ว่า outbox ทำให้ message ซ้ำได้ตรงไหน และระบบรับมืออย่างไร

1. ปัญหาเกิดจากอะไร

ข้อ 6 ใน quiz บทที่ 4 ถามว่าถ้า Kafka ล่มตอนมีไฟล์ใหม่เข้ามา จะเกิดอะไรขึ้น คำตอบคือไม่มีอะไรหาย เพราะ File Watcher ไม่ได้คุยกับ Kafka เลย ในโค้ดก็เป็นแบบนั้นจริง โปรเจกต์ API ไม่ได้อ้างถึง Confluent.Kafka สักบรรทัด มีแค่ Worker ที่ต่อ Kafka

ถ้าให้ API บันทึกงานแล้วส่ง Kafka เองจะง่ายกว่า แต่ PostgreSQL กับ Kafka เป็นระบบแยกกันสองตัว ไม่มี transaction ที่ครอบทั้งสองตัวได้ การเขียนลงสองที่ให้สำเร็จพร้อมกันหรือพังพร้อมกันจึงทำไม่ได้ตรง ๆ

2. ที่มาของ concept

เริ่มจากคำถามว่า “บันทึกงานแล้วส่ง message ต่อเลยไม่ได้หรือ” แล้วไล่คำถามที่ตามมา

  1. ถ้าเขียนฐานข้อมูลสำเร็จแต่ส่ง Kafka ไม่สำเร็จ หรือกลับกัน จะเกิดอะไร? งานค้างโดยไม่มีใครมาทำ หรือมี message ของงานที่ไม่มีอยู่จริง → 17 dual write
  2. ถ้าทำให้สองอย่างเป็น transaction เดียวกันไม่ได้ จะทำให้เหลือที่เดียวได้ไหม? เก็บ message ลงตารางในฐานข้อมูลเดียวกับงาน แล้ว commit พร้อมกัน → 18 transactional outbox
  3. message อยู่ในตารางแล้ว ใครส่งเข้า Kafka? ต้องมีตัวที่คอยอ่านตารางแล้วส่งต่อ ส่งไม่ผ่านก็ลองใหม่ → 19 message relay
  4. ตัวส่งต่อดับหลังส่งแล้วแต่ก่อนจดว่าส่งแล้ว จะเป็นอย่างไร? มันจะส่งซ้ำ ฝั่งรับต้องรับซ้ำได้ → 20 outbox ส่งซ้ำได้ ฝั่งรับต้อง idempotent

3. Concept หลัก 4 ข้อ

17

Dual write: เขียนสองที่ แต่พังได้ทีละที่

การเขียนลงสองระบบที่ไม่มี transaction ร่วมกันเรียกว่า dual write ไม่ว่าจะเรียงลำดับแบบไหน ก็มีจังหวะที่สำเร็จแค่ฝั่งเดียว ส่วนการใช้ distributed transaction (2PC) ครอบทั้งสองฝั่งมักทำไม่ได้ เพราะฐานข้อมูลหรือ broker ไม่รองรับ [microservices.io]

18

Transactional outbox: เก็บ message ไว้ที่เดียวกับงาน

แทนที่จะส่ง message ตรง ๆ ให้เขียน message ลงตาราง outbox ใน transaction เดียวกับข้อมูลงาน แล้วให้อีก process หนึ่งส่งเข้า broker ภายหลัง ถ้า transaction commit ผ่าน message ก็จะไปถึง broker แน่นอน [microservices.io]

19

Message relay: ตัวที่คอยส่ง outbox ออกไป

ตัวที่อ่าน outbox แล้วส่งต่อเรียกว่า message relay วิธีที่ง่ายที่สุดคือ poll ตาราง outbox เป็นระยะ (polling publisher) ข้อเสียคือส่งให้ถูกลำดับได้ยาก [microservices.io] อีกวิธีคืออ่านจาก transaction log ของฐานข้อมูล (transaction log tailing)

20

Outbox ส่งซ้ำได้ ฝั่งรับต้อง idempotent

relay อาจส่ง message เดิมมากกว่าหนึ่งครั้ง consumer จึงต้อง idempotent [microservices.io] outbox จึงต้องใช้คู่กับ concept 10 จากบทที่ 4 ทุกครั้ง

4. mapping-demo ใช้อย่างไร

ตาราง outbox สร้างใน 0003_file_jobs_outbox.sql มีคอลัมน์ topic, message_key, payload (jsonb), created_at และ sent_at ทุกจุดที่สร้างงานเรียก OutboxWriter.AddAsync ซึ่งบังคับให้ส่ง transaction เข้ามาด้วย message จึงไปกับ transaction ของงานเสมอ

ผู้เขียน outboxเขียนพร้อมกับอะไรtopic · key
FileIntake (API, เรียกจาก File Watcher)insert file job ใหม่file-import · fileJobId
FileJobService Retry (API)ตั้ง file job กลับเป็น Queuedfile-import · fileJobId
FileJobService Reprocess (API)สร้าง row job ใหม่ทุกแถวrow-normalize · sourceRowId
RowJobService Retry (API)ตั้ง row job กลับเป็น Pendingrow-normalize · sourceRowId
FileImportHandler (Worker)Source row และ row job ของแถวนั้น ทีละแถวrow-normalize · sourceRowId

OutboxDispatcher เป็นตัวเดียวที่ produce เข้า Kafka เป็น polling publisher ที่อ่านแถว sent_at IS NULL ทุก 500 ms เรียงตาม id ทีละไม่เกิน 100 แถว ส่งไม่ผ่านก็ break ออกจากรอบนั้น และไม่มีโค้ดลบแถวที่ส่งแล้ว ตาราง outbox จึงใช้ดูย้อนหลังได้ว่าเคยส่งอะไรไปเมื่อไร

ลองเล่น: ทำไม normalize เริ่มได้ก่อน import จบ

FileImportHandler เปิด transaction ใหม่ทุกแถว ใน transaction นั้นเขียน Source row, row job และ outbox แล้ว commit ทันที

ถ้าเปิด Worker สอง process จะมี OutboxDispatcher สองตัว ทั้งคู่อ่านแถวเดียวกันได้เพราะไม่มีการล็อก จึงส่งซ้ำได้ และลำดับก็อาจสลับ ความถูกต้องยังอยู่ได้เพราะ handler idempotent (concept 20) แต่จะเสีย message โดยเปล่าประโยชน์

5. ทบทวนโดยไม่เลื่อนขึ้นไปดู

1. ทำไม File Watcher ไม่ส่ง message เข้า Kafka เองหลังบันทึก file job?

  1. ถ้าส่งไม่ผ่านหลัง commit งานจะค้างโดยไม่มีใครทำ
  2. Kafka รับ message จากโปรเจกต์ API โดยตรงไม่ได้
  3. ส่ง Kafka ช้ากว่าการเขียนฐานข้อมูลหลายเท่าตัว
  4. File Watcher ไม่รู้ว่าจะต้องส่งไปที่ topic ไหน
PostgreSQL กับ Kafka ไม่มี transaction ร่วมกัน (dual write) ถ้าบันทึกงานแล้วส่ง message ไม่ผ่าน งานจะเป็น Queued ตลอดไป outbox แก้ด้วยการเก็บ message ไว้ใน transaction เดียวกับงาน

2. Kafka ล่มอยู่ 10 นาที ระหว่างนั้นวางไฟล์ใหม่ 3 ไฟล์ ตาราง outbox จะเป็นอย่างไร?

  1. มี 3 แถวใหม่ที่ sent_at ยังว่าง รอส่ง
  2. ว่างเปล่า เพราะ File Watcher รอ Kafka ก่อน
  3. มี 3 แถวที่ sent_at มีค่าแต่ส่งไม่สำเร็จ
  4. มีแถวเดียว เพราะส่งไม่ผ่านจึงรวมเป็นชุด
File Watcher ใช้แค่ PostgreSQL จึงสร้างงานและ outbox ได้ปกติ OutboxDispatcher ส่งไม่ผ่านก็ยังไม่บันทึก sent_at แล้วลองใหม่ทุก 500 ms

3. message ใน outbox ถูกส่งซ้ำได้ในจังหวะไหน?

  1. ส่งเข้า Kafka แล้ว แต่ดับก่อนบันทึก sent_at
  2. บันทึก sent_at แล้ว แต่ดับก่อนส่งเข้า Kafka
  3. File Watcher เขียน outbox ซ้ำทุก 500 ms
  4. Kafka ลบ message เก่าแล้วให้ส่งมาใหม่
dispatcher ส่งก่อนแล้วค่อยบันทึก sent_at ถ้าดับตรงกลาง รอบหน้าจะเห็นแถวนั้นยังว่างแล้วส่งอีกครั้ง ลำดับนี้เลือกให้ message ไม่หายโดยยอมให้ซ้ำ

4. Kafka ล่มตอนส่งแถว 22 จาก 22, 23, 24 dispatcher ทำอะไรต่อ?

  1. หยุดรอบนี้ แล้วรอบหน้าเริ่มใหม่จากแถว 22
  2. ข้าม 22 ไปส่ง 23 กับ 24 ก่อนแล้วค่อยกลับมา
  3. ลบแถว 22 ทิ้งแล้วตั้ง file job เป็น Failed
  4. ตั้ง sent_at ของ 22 ไว้แล้วส่งซ้ำวันถัดไป
ใน OutboxDispatcher เมื่อเจอ ProduceException จะ break ออกจากรอบ รอบถัดไปอ่านแถวที่ sent_at ว่างเรียงตาม id ใหม่ จึงเริ่มที่ 22 ก่อนเสมอ

5. ทำไม normalize แถวแรกเริ่มได้ ก่อนที่ import ทั้งไฟล์จะจบ?

  1. แต่ละแถว commit Source, row job, outbox ทันที
  2. Worker ส่ง message ทั้งไฟล์ไปตั้งแต่ก่อน import
  3. normalize อ่านไฟล์ CSV ตรงโดยไม่รอ Source Table
  4. File Watcher สร้าง row job ไว้ตอนวางไฟล์แล้ว
FileImportHandler เปิด transaction ใหม่ทุกแถว พอแถวหนึ่ง commit แล้ว outbox ของแถวนั้นก็พร้อมให้ dispatcher ส่งในรอบถัดไป

พรุ่งนี้ลองกลับมาทำอีกรอบโดยไม่อ่านเนื้อหาก่อน

6. ลองกับระบบจริง (ไม่บังคับ)

ทำตามสถานการณ์ B1 และ B3 ใน acceptance-test-guide.md รัน API กับ docker compose ตาม README แต่ยังไม่เปิด Worker

ทายก่อนลงมือ: ตอนที่ Worker ยังปิดอยู่ แถวใน outbox ของไฟล์นี้จะมีกี่แถว และมี topic อะไรบ้าง

  1. วางไฟล์แล้วดู outbox: 
    Copy-Item ./samples/acceptance/02-outbox-restart.csv ./input/orders/orders-restart.csv
docker compose exec -T postgres psql -U mapping -d mapping -c "SELECT id, topic, message_key, sent_at FROM outbox ORDER BY id;"
  2. เปิด Worker แล้วดู log Dispatched outbox message … partition … offset … จากนั้นรันคำสั่ง SELECT เดิมอีกรอบ ดูว่า sent_at มีค่าแล้ว และมีแถว mapping.row-normalize เพิ่มเข้ามาทีละแถวระหว่าง import
  3. จำลองการส่งซ้ำ ตั้งแถว row-normalize แถวแรกกลับเป็นยังไม่ส่ง: 
    docker compose exec -T postgres psql -U mapping -d mapping -c "UPDATE outbox SET sent_at = NULL WHERE id = (SELECT id FROM outbox WHERE topic = 'mapping.row-normalize' ORDER BY id LIMIT 1);"
  4. ดู log ของ Worker ว่ามี Skipping row job … because status is Done และนับ normalized_orders ของไฟล์นี้ว่ายังเท่าเดิม
