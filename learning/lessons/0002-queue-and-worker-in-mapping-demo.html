Queue กับ Worker ทำอะไรใน mapping-demo

ทำไม mapping-demo มีสองโปรแกรม และมี Kafka อยู่ตรงกลาง อธิบายด้วย concept จากบทที่ 1

สิ่งที่จะได้หลังจากจบบทนี้: วาดภาพรวมของ mapping-demo ได้ ชี้ได้ว่าส่วนไหนคือ producer, queue และ worker และอธิบายได้ว่าทำไมไม่ให้ API ทำงานทุกอย่างเอง

1. ปัญหา: งานบางอย่างช้าเกินกว่าจะรอ

ไฟล์หนึ่งไฟล์ใน mapping-demo ต้องผ่านขั้นตอนเยอะ: รอให้ไฟล์เขียนเสร็จ (Import:DelaySeconds), อ่านทีละแถวลง Source, normalize ทีละแถวลง Normalized, แล้วย้ายไฟล์ไป archive ถ้าให้ File Watcher ใน API ทำทั้งหมดเอง จะเจอปัญหาสามอย่าง

  • ค้าง: ระหว่างทำไฟล์หนึ่ง ไฟล์ถัดไปต้องรอคิว
  • หาย: ถ้า API ล่มกลางทาง งานที่ค้างอยู่ในหน่วยความจำหายไปด้วย
  • ขยายไม่ได้: อยากได้คนช่วยทำเพิ่ม ก็ต้องเพิ่ม API ทั้งก้อน

2. ทางออก: แยกคนสั่งงานออกจากคนทำงาน

“A message queue is a form of asynchronous service-to-service communication… a component called a producer adds a message to the queue… another component called a consumer retrieves the message and does something with it.” — AWS: Message Queues

แนวคิดนี้คือ decoupling (concept ข้อ 01 ในบทที่ 1) ลองนึกถึงร้านกาแฟ แคชเชียร์รับออเดอร์ เขียนบิลแปะไว้บนราง แล้วหันไปรับลูกค้าคนถัดไปทันที บาริสต้าหยิบบิลจากรางไปชงทีละใบ ถ้าบาริสต้าพักห้านาที บิลก็แค่รออยู่บนราง ไม่หายไปไหน

ร้านกาแฟศัพท์ใน mapping-demo
แคชเชียร์producer (ผู้สั่งงาน)File Watcher ใน API
บิลหนึ่งใบmessage (คำสั่งงานหนึ่งชิ้น){"fileJobId":1} มีแค่เลขงาน ไม่ได้แบกไฟล์มาด้วย
รางแปะบิลqueue (ที่พักงาน)Kafka (topic mapping.file-import)
บาริสต้าworker (ผู้หยิบงานไปทำ)โปรแกรม MappingDemo.Worker

message มีแค่เลขงาน เหมือนบิลที่เขียนแค่เลขออเดอร์ ส่วนรายละเอียดทั้งหมด (ไฟล์อยู่ไหน ใช้ config version ไหน) อยู่ในตาราง file_jobs ของ PostgreSQL Worker เอาเลขนี้ไปค้นต่อเอง

Kafka นิยามตัวเองว่าเก็บ event ไว้ใน topic ซึ่ง “very simplified, a topic is similar to a folder in a filesystem” — Apache Kafka: Introduction

ในโปรเจกต์นี้ Kafka คือรางแปะบิล แต่ละรางเรียกว่า topic และ mapping-demo มีสองราง

3. ภาพรวมทั้งระบบ: รูปแบบเดียวกันสองรอบ

สิ่งที่เห็นจากแผนภาพนี้

  1. Import worker เป็น worker ของรอบ 1 และเป็น producer ของรอบ 2 ไปพร้อมกัน
  2. งานหนึ่งแตกเป็นหลายงาน ไฟล์ orders-a.csv 100 แถวสร้าง message รอบแรก 1 อัน และรอบที่สองอีก 100 อัน
  3. แถวที่ 1 เริ่ม normalize ได้ทันทีขณะที่แถวที่ 2–100 ยัง import อยู่ ตรงกับที่ README บอกว่า normalize “ไม่ต้องรอให้ทั้งไฟล์ import เสร็จ”

ข้างในโปรแกรม Worker มีอะไรบ้าง

.NET เรียกโปรแกรมแบบนี้ว่า Worker Service; background service แต่ละตัวเป็น BackgroundService ที่วนทำงานไปจนโปรแกรมถูกสั่งหยุด — Microsoft Learn: Worker Services

ในโปรแกรม MappingDemo.Worker มี background service สามตัวรันพร้อมกัน แต่ละตัววนทำงานไปเรื่อย ๆ จนกว่าจะปิดโปรแกรม (ดูที่ src/MappingDemo.Worker/Program.cs บรรทัด AddHostedService):

Background serviceทำอะไร (แบบเข้าใจง่าย)
OutboxDispatcherบุรุษไปรษณีย์: ทุกครึ่งวินาที หยิบ message ที่รอส่งจากตาราง outbox ไปแปะลง Kafka
FileImportConsumerImport worker: หยิบงานจาก mapping.file-import ไปอ่านไฟล์ลง Source
RowNormalizeConsumerNormalize worker: หยิบงานจาก mapping.row-normalize ไปแปลงทีละแถว

ต้องมี “บุรุษไปรษณีย์” เพราะผู้สั่งงานไม่ได้แปะบิลลง Kafka เอง แต่หย่อนไว้ใน “กล่องจดหมายขาออก” (ตาราง outbox) ก่อน เหตุผลที่ต้องอ้อมแบบนี้อยู่ในบทที่ 6

4. ลองเล่น: ปิด Worker แล้วดูว่าเกิดอะไรขึ้น

ตัวจำลองนี้มีแค่รอบที่ 1 และไม่มีกล่องจดหมายขาออก Worker ใช้เวลาทำแต่ละงาน 2.5 วินาที

  1. กดวางไฟล์เร็ว ๆ 4 ครั้งติดกัน ฝั่ง API ต้องรอ Worker ไหม? ตัวเลข “ค้างรอ worker” เป็นอย่างไร?
  2. ปิด Worker แล้ววางไฟล์อีก 3 ไฟล์ งานหายไหม?
  3. เปิด Worker กลับมา มันทำต่อจากตรงไหน?
  4. ปิด Worker ระหว่างที่กล่องสีส้มกำลังทำอยู่ แล้วเปิดใหม่ งานชิ้นนั้นทำไปกี่ครั้ง? (นี่คือ at-least-once จากบทที่ 1 ส่วนวิธีที่ mapping-demo รับมืออยู่ในบทที่ 4)

กล่องที่ทำเสร็จแล้วยังอยู่บนราง Kafka ไม่ฉีกบิลทิ้งแบบร้านกาแฟ แต่เก็บไว้ระยะหนึ่ง แล้วให้ worker จำเองว่าทำถึงใบไหน

5. เฉลย: concept จากบทที่ 1 อยู่ตรงไหนในโปรเจกต์

เอาไปเทียบกับคำตอบที่เดาไว้ท้ายบทที่ 1

Conceptใน mapping-demo
01 DecouplingFile Watcher (API) แค่บันทึกงานแล้วไปทำอย่างอื่นต่อ Worker เป็นอีกโปรแกรมที่จะเปิดหรือปิดก็ได้ ระหว่างนั้นงานก็รอไว้ก่อน
02 Load levelingโยนไฟล์เข้ามาพร้อมกัน 20 ไฟล์ ก็ได้ 20 งานในคิว แล้ว Import worker ค่อย ๆ ทำทีละงานในจังหวะของตัวเอง (หน่วงตาม Import:DelaySeconds) API ไม่ช้าลงเลย
03 Competing consumersค่า Kafka:FileImportConsumers และ Kafka:NormalizeConsumers ใน appsettings คือจำนวน worker ที่ช่วยกันหยิบงานจากแต่ละ topic (ตอนนี้ตั้งไว้ที่ 1 ดูรายละเอียดในบทที่ 5)
04 Point-to-pointงาน import หนึ่งไฟล์ต้องทำแค่ครั้งเดียว worker ทุกตัวของ import จึงอยู่ในกลุ่มเดียวกัน (mapping-file-import) และแบ่งงานกัน ไม่ได้รับสำเนาซ้ำ
05 At-least-onceworker แจ้ง Kafka ว่าเสร็จ หลัง ทำงานจบเท่านั้น ถ้าดับกลางทาง งานจะกลับมาอีกรอบ ส่วนงานที่พัง ระบบจะบันทึกสถานะ Failed / ImportFailed ไว้ในฐานข้อมูล ให้คนสั่ง Retry ผ่าน API ได้ แทนการใช้ dead-letter queue (บทที่ 4)
Kafka = queue แบบ logmessage ที่ทำเสร็จแล้วยังอยู่ใน topic ให้ดูย้อนหลังได้ใน Kafka UI

6. ทบทวนโดยไม่เลื่อนขึ้นไปดู

1. message ที่ส่งเข้า mapping.file-import มีข้อมูลอะไร?

  1. เลขของ file job เพียงค่าเดียว
  2. เนื้อหาไฟล์ CSV ทั้งไฟล์ทุกแถว
  3. path ของไฟล์และ mapping config
  4. ผลลัพธ์แถวที่ normalize แล้ว
message มีแค่ fileJobId Worker เอาเลขนี้ไปค้นรายละเอียดในตาราง file_jobs เอง ข้อมูลจริงจึงอยู่ที่เดียวคือฐานข้อมูล

2. ไฟล์ CSV 100 แถวที่บันทึกลง Source ได้ครบ ทำให้เกิด message ทั้งหมดกี่อัน?

  1. 1 อันของไฟล์ บวก 100 อันของแถว
  2. 1 อันของไฟล์ทั้งไฟล์เท่านั้นเอง
  3. 100 อันของแถว ไม่มีของไฟล์เลย
  4. 2 อัน คือ import 1 และ normalize 1
รอบแรก: 1 message ต่อไฟล์ (mapping.file-import) รอบสอง: 1 message ต่อแถวที่บันทึกลง Source (mapping.row-normalize) รวม 101 อัน การที่งานหนึ่งแตกเป็นหลายงานแบบนี้ ทำให้ normalize ทำไปพร้อมกับ import ได้

3. ปิดโปรแกรม Worker ไว้แล้ววางไฟล์ใหม่ 3 ไฟล์ จะเกิดอะไร?

  1. ระบบเก็บงานไว้รอจน Worker กลับมาทำ
  2. API ค้างรอจนกว่า Worker จะกลับมา
  3. ไฟล์ถูกข้ามและหายไปจากระบบเลย
  4. API หันมา import ไฟล์ทั้งสามเอง
Watcher บันทึกงานแล้วทำงานต่อได้ทันที แต่ “บุรุษไปรษณีย์” (OutboxDispatcher) อยู่ในโปรแกรม Worker ด้วย ตอน Worker ปิด งานจึงรออยู่ในกล่องจดหมายขาออก (ตาราง outbox) ยังไม่ถึง Kafka ลองพิสูจน์ได้ในส่วนที่ 7

4. ในโปรแกรม MappingDemo.Worker มี background service อะไรบ้าง?

  1. ส่ง outbox เข้า Kafka, import ไฟล์, normalize แถว
  2. เฝ้าโฟลเดอร์ input, import ไฟล์, normalize แถว
  3. รับ HTTP request, import ไฟล์, normalize แถว
  4. สร้าง Kafka topic, import ไฟล์, normalize แถว
OutboxDispatcher, FileImportConsumer, RowNormalizeConsumer การเฝ้าโฟลเดอร์และรับ HTTP อยู่ฝั่ง API ส่วน topic สร้างด้วยสคริปต์ create-topics.ps1

5. ทำไมการหน่วง Import:DelaySeconds ไม่ทำให้ File Watcher ช้าลง?

  1. Watcher แค่บันทึกงานแล้วส่งต่อ ไม่รอผล
  2. Watcher ข้ามการหน่วงเมื่อไฟล์มีขนาดเล็ก
  3. Kafka เร่งความเร็วการ import ให้อัตโนมัติ
  4. การหน่วงเกิดก่อนที่ Watcher จะเห็นไฟล์
การหน่วงเกิดใน Import worker งานของ Watcher จบตั้งแต่บันทึกงานลงฐานข้อมูล จึงไม่ต้องรอการหน่วงนี้

พรุ่งนี้ลองกลับมาทำอีกรอบโดยไม่อ่านเนื้อหาก่อน จะจำได้นานกว่าการอ่านซ้ำ

7. ลองกับระบบจริง (ไม่บังคับ)

ต้องรันเดโมตาม README ไว้ก่อน (reset → API → configure → Worker)

ทายก่อนลงมือ: ถ้าปิด Worker แล้ววางไฟล์ใหม่ Kafka UI จะเห็น message ใหม่ไหม? เขียนคำตอบพร้อมเหตุผลไว้ก่อน แล้วค่อยลอง

  1. เปิด Kafka UI ที่ localhost:8080 → Topics แล้วดูว่าแต่ละ topic มี message กี่อัน
  2. กด Ctrl+C ที่ terminal ของ Worker
  3. รัน pwsh ./scripts/generate-sample.ps1 ไฟล์ควรค้างอยู่ใน input/orders
  4. ดู Kafka UI อีกครั้ง จำนวน message เปลี่ยนไหม? แล้วงานไปรออยู่ที่ไหน?
  5. เปิด Worker กลับมา (dotnet run --project src/MappingDemo.Worker) แล้วดู Kafka UI กับ GET http://localhost:5181/file-jobs คำทายของคุณถูกไหม?
