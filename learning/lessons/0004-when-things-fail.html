บทที่ 4 · ภาพรวม · ราว 20 นาที

เมื่อมีอะไรพัง: failure, retry และ reprocess

Worker ดับกลางงาน ข้อมูลบางแถวผิด Kafka ล่ม ระบบที่ใช้ queue ต้องรับมือกับเรื่องพวกนี้ได้ โดยงานไม่หายและไม่เกิดผลซ้ำ

สิ่งที่จะได้หลังจากจบบทนี้: ทำนายได้ว่า mapping-demo ทำอะไรเมื่อเกิดความล้มเหลวแต่ละแบบ และเลือกได้ว่าเมื่อไรควรใช้ Retry เมื่อไรควรใช้ Reprocess

1. ปัญหาเกิดจากอะไร

ในตัวจำลองของบทที่ 2 ถ้าปิด Worker ระหว่างที่งานกำลังทำอยู่ พอเปิดใหม่ Worker จะทำงานชิ้นนั้นอีกรอบ นี่คือ at-least-once จากบทที่ 1 ซึ่งทำให้เกิดคำถามตามมาสองข้อ งานที่ทำไปครึ่งทางจะเป็นอย่างไร และถ้าทำซ้ำ ข้อมูลจะซ้ำไหม

ใน mapping-demo มี API, Worker, Kafka และ PostgreSQL รันแยก process และคุยกันผ่านเครือข่าย ตัวไหนก็ดับหรือช้าได้ทุกเมื่อ ความล้มเหลวจึงเป็นเรื่องปกติที่ต้องออกแบบรองรับไว้ตั้งแต่แรก

2. ที่มาของ concept

เริ่มจากข้อเท็จจริงว่า worker ดับได้ทุกเมื่อ แล้วไล่คำถามที่ตามมาทีละข้อ

  1. worker ควรบอก queue ว่า “เสร็จแล้ว” ตอนไหน? ถ้าบอกก่อนทำ แล้วดับกลางทาง งานหาย ถ้าบอกหลังทำ งานไม่หาย แต่ worker อาจได้งานเดิมกลับมาทำซ้ำ → 09 delivery semantics
  2. ถ้าเลือกให้งานไม่หาย ก็ต้องยอมให้ทำซ้ำได้ แล้วจะกันข้อมูลซ้ำอย่างไร? ฝั่งรับต้องออกแบบให้ทำซ้ำแล้วได้ผลเหมือนทำครั้งเดียว → 10 idempotent receiver
  3. งานพังแล้ว ควรลองใหม่ทุกครั้งไหม? ไม่เสมอไป บาง error ลองใหม่อาจผ่าน บาง error ลองกี่รอบก็ผิด → 11 transient กับ permanent error
  4. ลองครบแล้วยังพัง จะเอางานนั้นไปไว้ไหน? ปล่อยวนไปเรื่อย ๆ ก็ขวางงานอื่น ทิ้งไปก็หาย จึงต้องพักไว้ให้คนดู → 12 งานที่พังถาวรต้องให้คนตัดสินใจ

3. Concept หลัก 4 ข้อ

09

Delivery semantics: commit ก่อนหรือหลัง

consumer เลือกได้ว่าจะบันทึกตำแหน่งที่อ่านถึง (commit) ก่อนหรือหลังทำงาน ถ้า commit ก่อนแล้วดับ งานนั้นหาย ถ้า commit หลังแล้วดับ งานนั้นจะกลับมาให้ทำซ้ำ [Kafka docs] ถ้าต้องเลือก at-least-once มักคุ้มกว่า เพราะงานซ้ำแก้ได้ด้วย idempotency แต่งานที่หายไปแล้วกู้คืนไม่ได้

10

Idempotent receiver: รับซ้ำได้ไม่เกิดผลซ้ำ

เมื่อเลือก at-least-once ฝั่งรับต้องรับ message เดิมซ้ำได้อย่างปลอดภัย [EIP] วิธีที่ใช้บ่อยมีสามแบบ เช็กสถานะก่อนทำ, ใช้ unique key ให้ insert ซ้ำไม่มีผล และ upsert ทับของเดิมด้วยค่าเดียวกัน

11

Transient กับ permanent error

error ชั่วคราวควร retry โดยรอนานขึ้นทุกรอบ (exponential backoff) และสุ่มระยะรอเพิ่มเล็กน้อย (jitter) เพื่อไม่ให้ทุกตัว retry พร้อมกันจนซ้ำเติมระบบ [AWS] ส่วน error ที่เกิดจากข้อมูลไม่ควร retry เพราะเสียเวลาเปล่า ให้บันทึกไว้แล้วไปทำงานอื่นต่อ

12

งานที่พังถาวรต้องให้คนตัดสินใจ

ลองครบแล้วยังพัง → พักไว้ → คนดูสาเหตุ → สั่งทำใหม่

หลายระบบย้ายงานแบบนี้ไป dead-letter queue (บทที่ 1) mapping-demo ใช้วิธีบันทึกสถานะ Failed ลงฐานข้อมูลแทน แล้วเปิด API ให้คนสั่งทำใหม่

4. mapping-demo รับมืออย่างไร

mapping-demo commit offset ของ Kafka หลัง handler ทำงานเสร็จ (EnableAutoCommit = false แล้วเรียก consumer.Commit เอง) จึงเป็น at-least-once และทุก handler ต้องรับ message ซ้ำได้

Handlerทำให้รับซ้ำได้อย่างไร
FileImportHandlerSource Table มี unique key (file_job_id, row_number) insert แถวที่มีแล้วจะได้ ON CONFLICT DO NOTHING และไม่สร้าง row job กับ message ซ้ำ ส่วนไฟล์ที่ Imported หรือ archive แล้วจะข้ามไปทำแค่ขั้นที่เหลือ
RowNormalizeHandlerเช็กสถานะก่อน ถ้า row job เป็น Done, Invalid หรือ Failed แล้วก็ข้าม และเขียน Normalized Table แบบ upsert ตาม source_row_id ทั้งหมดอยู่ใน transaction เดียว

ลองเล่น: Worker ดับกลาง import

แผนภาพนี้ตามสถานการณ์ B2 ใน acceptance-test-guide.md คือกด Ctrl+C ที่ Worker ตอน import ไปได้ 60 แถว แล้วเปิดใหม่

5. ทบทวนโดยไม่เลื่อนขึ้นไปดู

1. Worker ดับตอน import ไปได้ 60 แถวจาก 100 แล้วเปิดใหม่ เมื่องานจบ Source Table มีแถวของไฟล์นี้กี่แถว?

  1. 100 แถว เพราะระบบข้ามแถวที่มีอยู่แล้ว
  2. 160 แถว เพราะ import ใหม่ตั้งแต่แถวแรก
  3. 60 แถว เพราะงานจบไปตอนที่ Worker ดับ
  4. 40 แถว เพราะเริ่มใหม่จากแถวที่ 61 เท่านั้น
handler อ่านไฟล์ใหม่ตั้งแต่แถวแรกจริง แต่ unique key (file_job_id, row_number) ทำให้ระบบไม่ insert แถว 1 ถึง 60 ซ้ำ ผลรวมจึงเป็น 100

2. mapping-demo commit offset ของ Kafka ตอนไหน และได้ semantics แบบไหน?

  1. หลังทำงานเสร็จ จึงเป็น at-least-once
  2. ก่อนเริ่มทำงาน จึงเป็น at-least-once
  3. หลังทำงานเสร็จ จึงเป็น at-most-once
  4. ก่อนเริ่มทำงาน จึงเป็น exactly-once
commit หลังทำงาน ถ้าดับก่อน commit งานจะกลับมาให้ทำซ้ำ งานจึงไม่หายแต่อาจซ้ำ ตามนิยาม at-least-once ใน Kafka docs

3. แถว 25 มีวันที่ผิดรูปแบบ ระบบทำอย่างไรกับแถวนี้?

  1. ตั้งเป็น Invalid ทันที โดยไม่ลองใหม่
  2. ลองใหม่ 4 รอบ แล้วจึงตั้งเป็น Failed
  3. หยุด import ทั้งไฟล์เป็น ImportFailed
  4. ส่งแถวนี้ไปพักใน dead-letter queue
ข้อมูลผิดเป็น permanent error ลองกี่รอบก็ได้ผลเดิม ระบบจึงบันทึก Row Error แล้วทำแถวอื่นต่อ และ mapping-demo ก็ไม่มี dead-letter queue

4. normalize แถวหนึ่งพังเพราะฐานข้อมูลสะดุดชั่วคราว ระบบทำอย่างไร?

  1. ลองใหม่หลัง 1, 2, 4 วินาที ก่อนตั้ง Failed
  2. ตั้งเป็น Invalid ทันทีและบันทึก Row Error
  3. ลองใหม่ไปเรื่อย ๆ จนกว่าจะทำสำเร็จ
  4. ข้ามแถวนั้นไปโดยไม่บันทึกอะไรไว้เลย
transient error ควร retry แบบ backoff แต่ต้องมีเพดาน ไม่อย่างนั้นแถวที่พังจริงจะวนไม่จบ ครบ 4 รอบแล้วจึงตั้ง Failed ให้คนตัดสินใจ

5. แก้กฎวันที่ใน config version ใหม่แล้ว อยากให้แถว 25 ผ่าน ต้องทำอย่างไร?

  1. Reprocess ไฟล์นั้นพร้อมเลือก version ใหม่
  2. Retry row job ของแถว 25 ด้วย version เดิม
  3. วางไฟล์เดิมลง input/ ซ้ำอีกครั้งหนึ่ง
  4. รอให้ Worker ลองใหม่เองโดยอัตโนมัติ
Retry ใช้กฎรุ่นเดิมและใช้ได้เฉพาะงานที่ Failed ส่วนแถว 25 เป็น Invalid ถ้าวางไฟล์เดิมซ้ำ เนื้อหาจะซ้ำกับไฟล์เก่าและได้ Duplicate ทางเดียวที่ใช้กฎใหม่คือ Reprocess

6. Kafka ล่ม 5 นาที ขณะที่มีไฟล์ใหม่เข้ามา จะเกิดอะไรขึ้น?

  1. งานรออยู่ใน outbox แล้วส่งเมื่อ Kafka กลับมา
  2. File Watcher ปฏิเสธไฟล์จน Kafka กลับมา
  3. งานหายไป ต้องวางไฟล์ใหม่อีกรอบทั้งหมด
  4. Worker import ไฟล์จาก input/ เองโดยตรง
File Watcher ไม่ได้คุยกับ Kafka โดยตรง แค่เขียน file_jobs กับ outbox ลง PostgreSQL ส่วน OutboxDispatcher ส่งไม่สำเร็จก็ลองใหม่ทุกครึ่งวินาที บทที่ 6 จะดูว่าทำไมออกแบบแบบนี้

พรุ่งนี้ลองกลับมาทำอีกรอบโดยไม่อ่านเนื้อหาก่อน

6. ลองกับระบบจริง (ไม่บังคับ)

ทำตามสถานการณ์ B2 ใน acceptance-test-guide.md ต้องรันเดโมตาม README ไว้ก่อน ยกเว้น Worker ให้เปิดด้วยค่าที่ทำให้ import ช้าลง

ทายก่อนลงมือ: ถ้ากด Ctrl+C ตอน Source มี 40 แถว แล้วเปิด Worker ใหม่ rows กับ distinct_rows ตอนจบจะเป็นเท่าไร

  1. เปิด Worker แบบ import ช้า: 
    dotnet run --project src/MappingDemo.Worker -- `
    Import:DelaySeconds=1 `
    Demo:ImportRowDelayMs=200
  2. รัน pwsh ./scripts/generate-sample.ps1 แล้วเก็บ id ของงาน: 
    $job = Invoke-RestMethod http://localhost:5181/file-jobs |
    Where-Object fileName -eq "orders-a.csv"
  3. นับแถวใน Source จนได้ราว 10 ถึง 90 แถว: 
    docker compose exec -T postgres psql -U mapping -d mapping -c "SELECT count(*) FROM source_orders WHERE file_job_id = $($job.id);"
  4. กด Ctrl+C ที่ Worker แล้วเปิดใหม่ด้วยคำสั่งเดิม ดู log ว่า Worker ได้ message เดิมกลับมา
  5. เมื่อ importStatus เป็น Imported แล้ว ตรวจว่าไม่มีแถวซ้ำ: 
    docker compose exec -T postgres psql -U mapping -d mapping -c "SELECT count(*) AS rows, count(DISTINCT row_number) AS distinct_rows FROM source_orders WHERE file_job_id = $($job.id);"
