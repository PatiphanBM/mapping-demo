Lifecycle ของ file job

ฝากงานไว้ในคิวแล้ว จะรู้ได้อย่างไรว่างานเสร็จหรือยัง ตามรอย orders-a.csv ตั้งแต่วางไฟล์จนได้ผลลัพธ์ครบทุกแถว

สิ่งที่จะได้หลังจากจบบทนี้: อ่านผลของ GET /file-jobs/{id} แล้วบอกได้ว่าไฟล์อยู่ขั้นไหน ทำไมสถานะถึงเป็นแบบนั้น และงานจบแล้วหรือยัง

1. ปัญหาเกิดจากอะไร

ในบทที่ 1 และ 2 เราได้ข้อดีของ decoupling มาแล้ว คือ producer ฝากงานแล้วไปทำอย่างอื่นต่อได้ทันที แต่ข้อดีนี้มีราคา producer ไม่ได้รอ จึงไม่รู้ผล File Watcher สร้างงานเสร็จก็ไปทำอย่างอื่นต่อ ไม่มีใครบอกเราว่าไฟล์ orders-a.csv import ครบหรือยัง มีกี่แถวที่ไม่ผ่าน หรือพังไปกลางทางหรือเปล่า

2. ที่มาของ concept

ร้านซักรีดเจอปัญหาเดียวกัน ลูกค้าฝากผ้าแล้วกลับบ้าน ร้านไม่ได้โทรบอกเมื่อซักเสร็จ ลองไล่ดูว่าร้านต้องตอบคำถามอะไรบ้าง แต่ละคำตอบคือ concept หนึ่งข้อ

  1. ฝากไปแล้ว จะอ้างถึงงานชิ้นนี้ทีหลังได้อย่างไร? ร้านออกใบรับที่มีเลข และจดลงสมุดของร้าน → 06 job record
  2. ถามแล้ว ร้านจะตอบว่าอะไร? ร้านต้องจดความคืบหน้าไว้เป็นขั้น เช่น รับแล้ว กำลังซัก เสร็จแล้ว และรู้ว่าขั้นไหนคือจบ → 07 สถานะ
  3. ร้านไม่บอกเอง ลูกค้าจะรู้ได้อย่างไร? ลูกค้ามาถามเองด้วยเลขบนใบรับ ถามซ้ำจนได้คำตอบว่าเสร็จ → 08 status endpoint + polling

3. Concept หลัก 3 ข้อ

06

Job record: ใบรับงาน

ตอนรับงาน ระบบบันทึก job ไว้ในฐานข้อมูลก่อน แล้วใช้ id ของ job เป็นเลขอ้างอิงทั้งใน message และตอนถามสถานะ ถ้ารับงานผ่าน HTTP มักตอบด้วย 202 Accepted ซึ่งแปลว่า “รับงานแล้ว แต่ยังทำไม่เสร็จ” [HTTP spec]

07

สถานะที่ยังไปต่อได้ กับสถานะสุดท้าย

สถานะของงานเดินไปข้างหน้าทีละขั้น บางสถานะยังไปต่อได้ (non-terminal) บางสถานะคือจุดจบ (terminal) Microsoft แนะนำให้กำหนดชุดสถานะให้ชัดและเขียนเอกสารไว้ [Microsoft]

08

Status endpoint + polling

ฝั่งที่ทำงานไม่ส่งผลกลับมาเอง client จึงต้องถามซ้ำเป็นระยะ (polling) จนสถานะเป็น terminal คำตอบควรมีข้อมูลพอให้รู้ว่างานอยู่ขั้นไหน เช่น status, createdAt, lastUpdatedAt และ error [Microsoft] ถ้าไม่อยากให้ client ถามบ่อย ๆ ก็มีทางเลือกแบบ push เช่น webhook หรือ Server-Sent Events แต่ต้องทำเพิ่ม

4. mapping-demo ใช้ concept เหล่านี้อย่างไร

Conceptใน mapping-demo
06 Job recordFile Watcher สร้างแถวใน file_jobs พร้อม message ใน transaction เดียวกัน (FileIntake.CreateJobAsync) และ message มีแค่ fileJobId ส่วนตอน import แต่ละแถว Worker สร้าง row job ใน row_jobs แถวละหนึ่ง job
07 สถานะfile job มีสถานะสามแกนแยกกัน (ดูด้านล่าง) ส่วน row job มีแกนเดียว
08 Status endpointGET /file-jobs (เรียงงานใหม่สุดก่อน), GET /file-jobs/{id}, GET /file-jobs/{id}/errors และ GET /file-jobs/{id}/rows/{rowNumber}/history

ต่างจากระบบทั่วไปตรงที่งานไม่ได้เข้ามาทาง HTTP แต่เข้ามาเป็นไฟล์ในโฟลเดอร์ จึงไม่มีใครได้ 202 กลับไป ต้องหา id ของงานเองจาก GET /file-jobs

สถานะของ file job: สามแกนที่เดินแยกกัน

importStatus บอกว่า Import worker ทำถึงไหน

Queued→ Delaying→ Importing→ Importedหรือ ImportFailedหรือ Duplicate

Queued ตั้งโดย File Watcher ตอนสร้างงาน ที่เหลือตั้งโดย FileImportHandler ส่วน Duplicate คือไฟล์ที่เนื้อหาซ้ำกับไฟล์ที่เคยรับไว้แล้วภายใต้ config เดียวกัน

archiveStatus บอกว่าย้ายไฟล์ต้นฉบับไป archive แล้วหรือยัง

NotArchived→ Archivedหรือ ArchiveFailedหรือ ChangedAfterRead

ArchiveFailed กับ ChangedAfterRead (ไฟล์ต้นฉบับถูกแก้หลังระบบอ่านไปแล้ว) เป็นกรณีพิเศษ ดูได้ในสรุปเมื่อมีอะไรพัง

normalizationStatus ไม่ได้เก็บในตาราง แต่ API คำนวณจากจำนวน row job ทุกครั้งที่ถาม (NormalizationStatusCalculator)

InProgress→ Completedหรือ CompletedWithErrors

กติกามีสองข้อ ถ้า import ยังไม่ Imported หรือยังมี pendingRows มากกว่า 0 ให้เป็น InProgress ถ้าจบแล้วแต่มีแถว Invalid หรือ Failed ให้เป็น CompletedWithErrors

สถานะของ row job

Pending→ Doneหรือ Invalidหรือ Failed

Invalid คือข้อมูลในแถวไม่ผ่านกฎ normalize เช่น วันที่ผิดรูปแบบ ระบบบันทึกรายละเอียดเป็น Row Error Failed คือระบบพังระหว่างทำ Normalize worker ลองใหม่เองอีก 3 รอบ (เว้น 1, 2 และ 4 วินาที) ถ้ายังพังจึงตั้งเป็น Failed

สถานะสุดท้ายยังช่วยกันงานซ้ำด้วย ถ้า Kafka ส่ง message ของ row job ที่เป็น Done, Invalid หรือ Failed อยู่แล้วมาอีกรอบ RowNormalizeHandler จะข้ามไปเลย นี่คือวิธีหนึ่งที่ mapping-demo รับมือกับ at-least-once ซึ่งจะเจาะต่อในบทที่ 4

5. ลองเล่น: ดู orders-a.csv เปลี่ยนสถานะ

ไทม์ไลน์นี้จำลองผลของ GET /file-jobs/1 ระหว่างที่ระบบทำ orders-a.csv (100 แถว แถว 25 วันที่ผิด แถว 75 จำนวนเงินผิด) เวลาเป็นค่าประมาณตาม README (หน่วง 30 วินาที, ราว 100 ms ต่อแถว) แผนภาพสถานะด้านบนจะไฮไลต์สถานะปัจจุบัน และ field ใน JSON ที่เปลี่ยนจากขั้นก่อนหน้าจะมีสีเน้น

ตัด field บางตัวออกให้อ่านง่าย ของจริงมี configId, configVersionId, createdAt และ updatedAt ด้วย

ลองตอบจากไทม์ไลน์: ในช่วงไหนที่ import กับ normalize ทำงานพร้อมกัน และทำไม totalRows ถึงเพิ่งมีค่าตอน Imported

6. ทบทวนโดยไม่เลื่อนขึ้นไปดู

1. วาง orders-a.csv ลง input/ ขณะที่ Worker ปิดอยู่ แล้วเรียก GET /file-jobs/{id} จะเห็น importStatus เป็นอะไร?

  1. Queued
  2. Delaying
  3. Importing
  4. Imported
File Watcher อยู่ใน API จึงยังสร้างงานได้และตั้งสถานะ Queued แต่สถานะถัดไปทั้งหมดตั้งโดย Worker ซึ่งปิดอยู่

2. importStatus=Imported, pendingRows=0, invalidRows=2, failedRows=0 แล้ว normalizationStatus เป็นอะไร?

  1. CompletedWithErrors เพราะมีแถวไม่ผ่าน
  2. Completed เพราะไม่มีแถวค้างแล้ว
  3. InProgress เพราะยังต้องแก้แถวที่ผิด
  4. ImportFailed เพราะบางแถวมีข้อผิดพลาด
import จบและไม่มีแถว Pending แล้ว แต่มีแถว Invalid จึงเป็น CompletedWithErrors แถวที่ผิดไม่ได้ทำให้ import ล้ม เพราะแถวอื่นยังบันทึกได้

3. importStatus=Importing, pendingRows=0, doneRows=40 แล้ว normalizationStatus เป็นอะไร?

  1. InProgress เพราะ import ยังไม่จบ
  2. Completed เพราะไม่มีแถวค้างแล้ว
  3. CompletedWithErrors เพราะยังไม่ครบ
  4. Delaying เพราะ Worker ยังหน่วงอยู่
กติกาข้อแรก ถ้า import ยังไม่ Imported ให้เป็น InProgress เสมอ ช่วงที่ pendingRows เป็น 0 แปลว่า Normalize worker ทำทัน Import worker เท่านั้น ยังไม่ได้แปลว่าจบ

4. เห็น archiveStatus=Archived แต่ normalizationStatus=InProgress เป็นไปได้ไหม?

  1. ได้ เพราะ archive ไม่ต้องรอ normalize
  2. ไม่ได้ ต้อง normalize เสร็จก่อน archive
  3. ได้ แต่เฉพาะตอนที่ Worker ล่มอยู่เท่านั้น
  4. ไม่ได้ เพราะสองสถานะนี้ขัดแย้งกันเอง
Import worker ย้ายไฟล์ไป archive ทันทีที่ import ครบ ส่วน normalize เป็นงานอีก queue หนึ่งที่เดินแยกกัน

5. ทำไม mapping-demo ต้องเก็บสถานะงานไว้ใน PostgreSQL ทั้งที่มี Kafka อยู่แล้ว?

  1. Kafka ไม่รู้ว่างานแต่ละชิ้นได้ผลอย่างไร
  2. Kafka ลบ message ทันทีที่อ่านเสร็จแล้ว
  3. Kafka เก็บ message ไว้ได้ไม่เกินหนึ่งวัน
  4. ตาราง file_jobs ช่วยให้ Kafka ทำงานเร็วขึ้น
Kafka รู้แค่ว่ามี message อะไร และ consumer อ่านถึงไหนแล้ว แต่ไม่รู้ว่าทำแล้วได้ผลอย่างไร ผลอย่าง “Invalid 2 แถว” มีแต่ worker ที่รู้ จึงต้องบันทึกลงฐานข้อมูล ส่วนตัวเลือกข้อ 2 ผิดตามที่เรียนในบทที่ 1 ว่า Kafka ไม่ลบ message หลังอ่าน

6. row job ที่เป็น Invalid ต่างจาก Failed อย่างไร?

  1. Invalid คือข้อมูลผิดกฎ Failed คือระบบพัง
  2. Invalid คือระบบพัง Failed คือข้อมูลผิดกฎ
  3. Invalid ยังรอ retry ส่วน Failed จบแล้ว
  4. ทั้งสองอย่างหมายถึงสิ่งเดียวกันทุกประการ
Invalid มาจากกฎ normalize ซึ่งลองใหม่กี่รอบก็ได้ผลเดิม Failed มาจาก exception ที่ยังพังหลังลองครบ 4 รอบ ทั้งสองเป็นสถานะสุดท้ายเหมือนกัน

พรุ่งนี้ลองกลับมาทำอีกรอบโดยไม่อ่านเนื้อหาก่อน

7. ลองกับระบบจริง (ไม่บังคับ)

รันเดโมตาม README ให้ครบทั้ง API และ Worker แล้วเปิด PowerShell อีกหน้าต่างหนึ่ง

ทายก่อนลงมือ: ระหว่างที่ importStatus ยังเป็น Importing ตัวเลข doneRows จะขยับไหม?

  1. รัน pwsh ./scripts/generate-sample.ps1
  2. poll สถานะของงานล่าสุดทุก 2 วินาที (กด Ctrl+C เพื่อหยุด): 
    $id = (Invoke-RestMethod http://localhost:5181/file-jobs)[0].id
while ($true) {
  Invoke-RestMethod "http://localhost:5181/file-jobs/$id" |
    Format-Table importStatus,archiveStatus,normalizationStatus,pendingRows,doneRows,invalidRows,failedRows
  Start-Sleep 2
}
  3. พอ normalizationStatus เป็นสถานะสุดท้ายแล้ว ให้ดูว่าแถวไหนไม่ผ่านเพราะอะไร: 
    Invoke-RestMethod "http://localhost:5181/file-jobs/$id/errors" | Format-Table

[0] คืองานล่าสุด เพราะ GET /file-jobs เรียงจาก id มากไปน้อย ถ้า generate-sample.ps1 สร้างสองไฟล์ ให้ลองเปลี่ยนเป็น [1] เพื่อดูอีกไฟล์
