Reference

อภิธานศัพท์ Queue & Worker

ภาษากลางของคอร์สนี้ ทุกบทใช้คำตามหน้านี้ ศัพท์โดเมน (Source Table, File Import Job ฯลฯ) ดูที่ CONTEXT.md

เคยเจอแล้ว มีอยู่ในบทเรียนแล้ว · เข้าใจแล้ว อธิบายหรือใช้ได้ถูกต้องแล้ว

พื้นฐาน

message เคยเจอแล้ว
คำสั่งงานหรือเหตุการณ์หนึ่งชิ้นที่ส่งผ่าน queue ใน mapping-demo มีแค่ id เช่น {"fileJobId":1} เลี่ยง: event, record (Kafka docs ใช้ทั้งสองคำ คอร์สนี้ใช้ message ตามชื่อคลาสในโค้ด)
producer เคยเจอแล้ว
โปรแกรมที่ส่ง message เข้า queue ใน mapping-demo คือ File Watcher (รอบ import) และ Import worker (รอบ normalize) เลี่ยง: publisher, sender
queue เคยเจอแล้ว
ที่พัก message ระหว่าง producer กับ consumer ทำให้ทั้งสองฝั่งไม่ต้องรอกันและไม่ต้องทำงานพร้อมกัน
topic เคยเจอแล้ว
queue หนึ่งรางใน Kafka (ต่างจาก queue ทั่วไปตรงที่ message ไม่ถูกลบทันทีหลังทำเสร็จ) ใน mapping-demo มี mapping.file-import กับ mapping.row-normalize เลี่ยง: channel, queue (เมื่อพูดถึง Kafka โดยเฉพาะ)
consumer เคยเจอแล้ว
โปรแกรมที่อ่าน message จาก topic แล้วทำงานตามนั้น เช่น FileImportConsumer
worker เคยเจอแล้ว
process ที่รันค้างไว้เพื่อทำงานเบื้องหลัง ใน mapping-demo คือ MappingDemo.Worker ซึ่งรัน background service สามตัว: OutboxDispatcher, FileImportConsumer, RowNormalizeConsumer เลี่ยงใช้สลับกับ consumer: worker คือโปรเซส, consumer คือบทบาทอ่าน message ภายในโปรเซส
outbox เคยเจอแล้ว
ตารางใน PostgreSQL ที่เก็บ message รอส่ง เขียนใน transaction เดียวกับข้อมูลงาน แล้ว OutboxDispatcher ค่อยส่งเข้า Kafka (“กล่องจดหมายขาออก” รายละเอียดบทที่ 6)

Concept

decoupling เคยเจอแล้ว
การแยก producer กับ worker ออกจากกันด้วย queue ทั้งสองฝั่งจึงไม่ต้องรอกัน ไม่ต้องเร็วเท่ากัน และไม่ต้องเปิดพร้อมกัน
load leveling เคยเจอแล้ว
การใช้ queue เป็นกันชนพักงานที่เข้ามาเป็นระลอก ให้ worker ทำในจังหวะคงที่ของตัวเอง เลี่ยง: buffering (ใช้ได้ แต่คอร์สนี้ใช้ load leveling)
competing consumers เคยเจอแล้ว
worker หลายตัวที่ช่วยกันหยิบงานจาก queue เดียวกัน โดยงานแต่ละชิ้นมี worker ทำแค่ตัวเดียว
point-to-point / publish-subscribe เคยเจอแล้ว
point-to-point: message หนึ่งชิ้นไปถึงผู้รับเพียงรายเดียว (เหมาะกับ “งาน”) · publish-subscribe: ผู้ติดตามทุกรายได้คนละหนึ่งสำเนา (เหมาะกับ “ข่าว”)
at-least-once เคยเจอแล้ว
การรับประกันว่า message แต่ละชิ้นจะได้ทำอย่างน้อยหนึ่งครั้ง ไม่หายแต่อาจซ้ำ เพราะ worker ที่ดับก่อนแจ้งว่าเสร็จจะได้งานเดิมกลับมาทำอีกรอบ
idempotent เคยเจอแล้ว
คุณสมบัติของ worker ที่ทำ message เดิมซ้ำกี่รอบก็ได้ผลลัพธ์เหมือนทำครั้งเดียว
dead-letter queue เคยเจอแล้ว
queue สำหรับพัก message ที่ทำไม่สำเร็จถาวร เพื่อไม่ให้ไปขวางงานอื่น (mapping-demo ไม่มี DLQ แต่ใช้สถานะ Failed ในฐานข้อมูลแทน)
job record เคยเจอแล้ว
แถวในฐานข้อมูลที่สร้างตอนรับงาน ใช้ id เป็นเลขอ้างอิงทั้งใน message และตอนถามสถานะ ใน mapping-demo คือแถวใน file_jobs และ row_jobs เลี่ยง: ticket, task (ใช้ได้ในบทเปรียบเทียบเท่านั้น)
terminal / non-terminal state เคยเจอแล้ว
terminal state คือสถานะสุดท้ายที่งานไม่เปลี่ยนต่อเอง เช่น Imported, Done ส่วน non-terminal state คือสถานะระหว่างทาง เช่น Queued, Pending
status endpoint / polling เคยเจอแล้ว
status endpoint คือ API ที่ตอบสถานะปัจจุบันของงาน polling คือการที่ client เรียก API นี้ซ้ำเป็นระยะจนได้ terminal state ใน mapping-demo คือ GET /file-jobs/{id}
delivery semantics เคยเจอแล้ว
การรับประกันว่า message แต่ละชิ้นจะได้ทำกี่ครั้ง at-most-once (อาจหายแต่ไม่ซ้ำ), at-least-once (ไม่หายแต่อาจซ้ำ), exactly-once (ครั้งเดียวพอดี) ฝั่ง consumer กำหนดได้ด้วยการเลือกว่าจะ commit ก่อนหรือหลังทำงาน
idempotent receiver เคยเจอแล้ว
handler ที่รับ message เดิมซ้ำได้โดยไม่เกิดผลซ้ำ ใน mapping-demo ทำด้วยการเช็กสถานะก่อนทำ, unique key กับ ON CONFLICT DO NOTHING และ upsert
transient / permanent error เคยเจอแล้ว
transient error คือ error ชั่วคราวที่ลองใหม่อาจผ่าน เช่น ฐานข้อมูลสะดุด ส่วน permanent error ลองกี่รอบก็ได้ผลเดิม เช่น ข้อมูลผิดกฎ
exponential backoff เคยเจอแล้ว
การ retry โดยรอนานขึ้นเป็นเท่าตัวในแต่ละรอบ เช่น 1, 2, 4 วินาที มักเติม jitter (สุ่มระยะรอเพิ่ม) เพื่อไม่ให้ client ทุกตัว retry พร้อมกัน
Retry / Reprocess เคยเจอแล้ว
Retry คือทำงานที่ล้มเหลวซ้ำด้วยข้อมูลและ config version เดิม Reprocess คือ normalize Source ใหม่ทั้งไฟล์โดยเลือก config version ได้ นิยามเต็มอยู่ใน CONTEXT.md เลี่ยงใช้สลับกัน: สองคำนี้มีความหมายต่างกันในโปรเจกต์นี้
partition เคยเจอแล้ว
แถวย่อยของ topic แต่ละแถวเรียง message ตามลำดับที่เข้ามา ใน consumer group หนึ่ง partition มี consumer ถือได้ตัวเดียว จำนวน partition จึงเป็นเพดานของงานที่ทำพร้อมกันได้ ทั้งสอง topic ใน mapping-demo มี 3 partition
consumer group เคยเจอแล้ว
ชื่อทีมของ consumer (GroupId) ตัวที่อยู่ group เดียวกันแบ่ง partition กัน คนละ group ได้ message ครบทุกชิ้น ใน mapping-demo คือ mapping-file-import และ mapping-row-normalize
message key เคยเจอแล้ว
ค่าที่ producer แนบไปกับ message ใช้เลือก partition key เดียวกันลง partition เดียวกันเสมอ ใน mapping-demo คือ fileJobId (file-import) และ sourceRowId (row-normalize)
rebalance เคยเจอแล้ว
การที่ Kafka แจก partition ใหม่ทุกครั้งที่มี consumer เข้าหรือออกจาก group Worker เขียน log assigned partitions ทุกครั้งที่เกิด
dual write เคยเจอแล้ว
การเขียนลงสองระบบที่ไม่มี transaction ร่วมกัน เช่น PostgreSQL กับ Kafka มีจังหวะที่สำเร็จแค่ฝั่งเดียวเสมอ
transactional outbox เคยเจอแล้ว
เขียน message ลงตาราง outbox ใน transaction เดียวกับข้อมูลงาน แล้วให้ message relay ส่งเข้า broker ทีหลัง ใน mapping-demo ทุกจุดเขียนผ่าน OutboxWriter.AddAsync
message relay / polling publisher เคยเจอแล้ว
ตัวที่อ่าน outbox แล้วส่งต่อเข้า broker แบบ polling คือ poll ตารางเป็นระยะ ใน mapping-demo คือ OutboxDispatcher (ทุก 500 ms, ทีละ 100 แถว, เรียงตาม id)
