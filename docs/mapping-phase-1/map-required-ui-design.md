# Map required — ตั้งเงื่อนไขด้วยตัวเลือก

## เป้าหมาย

ตามคำขอผู้ใช้วันที่ 2026-11-25 และภาพ Rule Editor ที่แนบ: ผู้ใช้ตั้งเงื่อนไขเลือกแถวและเลือกรายการที่จะส่งได้โดยไม่ต้องเขียน JSON ใช้ PrimeNG 21 และหน้าตาของระบบเดิมตาม D-78; ใช้ Transformation Program เดิมตาม M-03 โดยไม่เพิ่มกฎธุรกิจ

## หน้าจอที่เสนอ

เปลี่ยนหัวข้อ `Map required แล้ว 0 / 0` เป็น `จับคู่ข้อมูลปลายทาง` พร้อมข้อความ `จับคู่ช่องบังคับแล้ว 0 จาก 0 ช่อง` และปุ่ม `จับคู่ตามชื่อคอลัมน์`

ตัวอย่างรูปแบบเงื่อนไข (ชื่อคอลัมน์สมมติ ไม่ใช่ข้อกำหนดธุรกิจ):

```text
เลือกแถวที่จะส่ง
ส่งทุกแถว / ส่งเฉพาะแถวที่ตรงเงื่อนไข

ตรง [ครบทุกข้อ ▾]                 [+ เพิ่มเงื่อนไข] [+ เพิ่มกลุ่ม]
  [reference ▾]  [ไม่ว่าง ▾]                                  [ลบ]
  ตรง [อย่างน้อยหนึ่งข้อ ▾]       [+ เพิ่มเงื่อนไข] [+ เพิ่มกลุ่ม] [ลบกลุ่ม]
    [record_type ▾] [เท่ากับ ▾] [ข้อความ ▾] [A]                [ลบ]
    [record_type ▾] [เท่ากับ ▾] [ข้อความ ▾] [B]                [ลบ]
```

- แต่ละเงื่อนไขเลือกคอลัมน์จากขั้นที่ 1 แบบค้นหาได้ ตามด้วยวิธีตรวจและค่าที่ใช้เปรียบเทียบ; วิธีตรวจ `ว่าง` / `ไม่ว่าง` ไม่แสดงช่องค่า
- กลุ่มเลือก `ครบทุกข้อ` (`and`) หรือ `อย่างน้อยหนึ่งข้อ` (`or`) พร้อมเส้นเยื้องให้เห็นขอบเขตกลุ่ม; ปุ่มลบมีชื่อที่อ่านได้ด้วยโปรแกรมอ่านหน้าจอ
- รองรับการตรวจค่าว่าง และเปรียบเทียบเท่ากับ/ไม่เท่ากับ/มากกว่า/ตั้งแต่/น้อยกว่า/ไม่เกิน ตาม capabilities ที่ API ประกาศ; ข้อความเป็นค่าเริ่มต้น ตัวเลขต้องเลือกชนิดและแปลงต้นทางอย่างชัดเจน เพราะ Source เก็บข้อความตาม M-40
- แสดงประโยคสรุปเงื่อนไขและข้อผิดพลาดข้างช่องที่ยังไม่ได้เลือก; กลุ่มว่างหรือคอลัมน์ที่ถูกลบจากขั้นที่ 1 ต้องแจ้งให้แก้ก่อน Preview/บันทึก ไม่ปล่อยให้หมายถึงส่งทุกแถวโดยเงียบ ๆ
- เงื่อนไขของแต่ละรายการใน array ใช้ตัวเลือกชุดเดียวกัน มีค่าเริ่มต้น `ส่งรายการนี้เสมอ` และคำอธิบายว่ารายการที่ไม่จับคู่ข้อมูลใดจะไม่ถูกส่งตามพฤติกรรมเดิม
- เปลี่ยน `รายการใน array` เป็น `รายการข้อมูลที่ส่งได้หลายรายการ`; แสดง path เดิมเพื่ออ้างอิงโดยไม่เดาชื่อธุรกิจจากชื่อ field
- ตารางปลายทางใช้คำ `ช่องข้อมูลปลายทาง` / `ใช้ค่าจาก` / `สถานะ`, `เลือกข้อมูล` / `แก้ไข`, และ `จับคู่แล้ว` / `ยังไม่จับคู่` / `ไม่บังคับ`; คงเครื่องหมายช่องบังคับและปุ่มตั้งค่าการแปลงเดิม
- เก็บ `data-tour` เดิมและปรับคำอธิบาย tour ให้ตรงกับตัวเลือกใหม่

## ตัวอย่างข้อมูล → Transformation Program

แถวสมมติ `{ "reference": "SYNTHETIC-001", "record_type": "A" }` ตรงเงื่อนไขตัวอย่าง ส่วนแถว `{ "reference": "", "record_type": "A" }` ไม่ตรง:

```json
{
  "sourceWhen": {
    "kind": "and",
    "operands": [
      { "kind": "notBlank", "input": { "kind": "source", "field": "reference" } },
      {
        "kind": "or",
        "operands": [
          { "kind": "eq", "left": { "kind": "source", "field": "record_type" }, "right": { "kind": "literal", "value": "A" } },
          { "kind": "eq", "left": { "kind": "source", "field": "record_type" }, "right": { "kind": "literal", "value": "B" } }
        ]
      }
    ]
  }
}
```

เงื่อนไขของรายการใช้ Predicate รูปเดียวกันใน `emitWhen` ตาม API เดิม

## ความเข้ากันได้และการตรวจรับ

- โปรแกรมเดิมที่มี expressions หรือ predicates นอกแบบฟอร์มต้องคงข้อมูลครบ เปิดส่วน `ขั้นสูง (JSON)` เฉพาะกรณีจำเป็น; ไม่แปลงเป็นเงื่อนไขใหม่จนสูญเสียความหมาย
- การไม่มีเงื่อนไขยังหมายถึงส่งทุกแถว/ส่งรายการเสมอ; การกรอกไม่ครบต้องไม่ทำให้เงื่อนไขหายไปตอนบันทึก
- ตรวจเพิ่ม/ลบเงื่อนไขและกลุ่มซ้อน, เปิด version เดิม, คอลัมน์ถูกเปลี่ยนชื่อ/ลบ, เปรียบเทียบข้อความกับตัวเลข และการสร้าง `sourceWhen`/`emitWhen` กลับเป็นโปรแกรมเดิม
- ทดสอบ logic ที่แยกเป็นฟังก์ชันตามกฎ Web และรัน `npm run build` / `npm run test:ci`; ใช้ Preview เดิมตรวจแถวตัวอย่างเมื่อระบบ Local พร้อม
