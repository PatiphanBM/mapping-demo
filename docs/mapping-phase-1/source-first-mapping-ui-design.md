# จับคู่จากข้อมูลต้นทางและจัดการใน modal

## คำขอและขอบเขต

ผู้ใช้ 2026-11-25 ขอให้ตารางจับคู่ยึดข้อมูลต้นทางเป็นหลัก เลือก map ไปยังปลายทางผ่าน modal และรวมการจัดการ array; ปรับต่อจาก M-42–M-44 โดยใช้ Transformation Program/contract เดิม ไม่เปลี่ยนกฎธุรกิจหรือ API

## หน้าหลัก

ฝั่งซ้าย 60% ยังคงรายละเอียดปลายทางแบบย่อและส่วนจับคู่ข้อมูล ฝั่งขวาเป็น Preview sticky 40%:

| ข้อมูลต้นทาง | จับคู่ไปยังปลายทาง | สถานะ | จัดการ |
|---|---|---|---|
| reference | inform.reference | จับคู่แล้ว | จัดการ |
| first_name | inform.fullName | จับคู่แล้ว | จัดการ |
| last_name | inform.fullName | จับคู่แล้ว | จัดการ |
| extra_code | — | ยังไม่ใช้ | จับคู่ |

- แต่ละแถวคือ Key ในขั้นที่ 1 ใช้ header เป็นข้อมูลประกอบเมื่อมี; ค้นหาชื่อต้นทาง/ปลายทาง และกรองยังไม่ใช้/ต้องแก้ไขได้; ตามคำขอผู้ใช้เพิ่มเติม ไม่แสดงคอลัมน์หรือค่าตัวอย่างในตารางและ modal จับคู่
- คอลัมน์ปลายทางแสดงได้หลายรายการต่อหนึ่งต้นทาง; หนึ่ง expression ที่ใช้หลายคอลัมน์ปรากฏในทุกแถวที่เกี่ยวข้อง แต่เก็บ assignment เพียงชุดเดียวตาม target path
- ส่วนหัวคงจำนวนช่องบังคับปลายทางที่จับคู่แล้ว และปุ่ม `จัดการการจับคู่` เพื่อเปิด modal ได้แม้ยังไม่มีต้นทางถูกเลือก
- เงื่อนไขเลือกแถวและการ์ด array เดิมย้ายเข้า modal หน้าหลักแสดงเพียงสรุป เช่น `ส่งทุกแถว` / `มีเงื่อนไข` และจำนวนรายการที่ตั้งค่า
- ใต้ตารางมีทางเข้าจัดการ `ค่าอื่น (ค่าคงที่ / ข้อมูลไฟล์)` และ `การจับคู่ที่ต้องแก้ไข` เพื่อไม่ซ่อน expressions ที่ไม่มี Source field หรืออ้างถึง field ที่ลบไป; ไม่สร้าง Source field ปลอมลงโปรแกรม
- Source ที่ยังไม่ใช้ไม่ถือเป็นข้อผิดพลาด เพราะไม่จำเป็นต้องใช้ทุกคอลัมน์; ช่องบังคับของปลายทางยังตรวจเช่นเดิม

## Modal: จัดการการจับคู่

ใช้ modal เดียวมี 2 ส่วนสลับดูได้:

### 1. จับคู่ข้อมูล

- เปิดจากแถว → เลือกข้อมูลต้นทางแถวนั้นไว้ล่วงหน้า พร้อมรายการปลายทางที่ใช้อยู่ โดยไม่แสดงค่าตัวอย่าง
- เลือกปลายทางแบบค้นหาได้ แล้วเลือกว่าจะใช้ค่าตรง ๆ หรือตั้งการแปลงด้วย Value Expression Editor เดิม เช่น trim/แปลงชนิด/ต่อข้อความ
- เพิ่มปลายทางได้หลายช่องสำหรับต้นทางเดียว และแก้ expression ที่ใช้หลายคอลัมน์ได้โดยมีข้อความบอกว่าปลายทางนั้นใช้คอลัมน์ใดร่วมกัน
- ถ้าปลายทางถูกจับคู่แล้ว ให้เปิดค่าเดิมให้แก้ ไม่เขียนทับโดยเงียบ; การนำ assignment ออกหมายถึงนำการจับคู่ของ target path นั้นออกจากฉบับร่าง ไม่ใช่ลบเฉพาะการแสดงในแถวต้นทางใดแถวหนึ่ง
- ตัวเลือก `ค่าอื่น (ค่าคงที่ / ข้อมูลไฟล์)` เปิดแก้ assignment ที่ไม่อ่านต้นทาง รวมถึง advanced expressions เดิม; ต้นทางที่ถูกลบต้องมีรายการเตือนและเปิดแก้ได้
- แสดงช่องบังคับปลายทางที่ยังขาด เพื่อให้เลือกเติมได้โดยไม่ต้องกลับไปใช้ตารางปลายทางเป็นหน้าหลัก
- ปุ่มจับคู่ตามชื่อคอลัมน์อยู่ใน modal และทำกับฉบับร่างเท่านั้น

### 2. รายการและเงื่อนไข

- เลือกแถวที่จะส่งด้วย Predicate Editor เดิม
- เลือกกลุ่ม array ตาม schema แล้วเพิ่ม/ลบรายการ เลือกรายการที่จะตั้งค่า และกำหนดเงื่อนไขส่งแต่ละรายการ
- เมื่อจับคู่ไปยัง array เลือกรายการ เช่น `inform.beneficiaries[1]` ก่อนเลือกช่องปลายทาง และเพิ่มรายการใหม่จากบริบทนั้นได้; สามารถกลับส่วนจับคู่เพื่อตั้ง field ของรายการที่เลือกใน modal เดิม
- กลุ่มซ้อนแสดง path ของ parent และลำดับรายการชัดเจน; ลบรายการสุดท้ายตามพฤติกรรมเดิมและล้างเฉพาะ draft ของรายการ/กลุ่มลูกนั้น ไม่กระทบรายการอื่น
- รายการที่ไม่จับคู่ field ใดจะไม่ถูกส่งตามกลไกเดิม ไม่เพิ่มกฎผู้รับประโยชน์หรือข้อมูลธุรกิจเอง

## การยืนยันและยกเลิก

- เปิด modal แล้วคัดลอก assignments, item counts, item conditions และ sourceWhen เป็นฉบับร่างของหน้าต่างนั้น
- เพิ่ม/แก้/นำ mapping ออก, auto-map, เปลี่ยน array/เงื่อนไข → ยังไม่เปลี่ยนตารางหลักหรือ Preview
- Footer: `ยกเลิก` / `ใช้การตั้งค่านี้`; ใช้สำเร็จแล้วอัปเดต state ทั้งชุดพร้อมกันและล้างผล Preview เก่าที่ไม่ตรงค่าล่าสุด
- ยกเลิก/ปิด/Escape → ทิ้ง draft คง mapping/array/เงื่อนไข/Preview เดิม และคืน focus ให้ปุ่มที่เปิด modal
- ตรวจ target ซ้ำ/target ที่ไม่มีแล้ว/คอลัมน์ที่หายไป/เงื่อนไขผิดใน draft; ช่องบังคับปลายทางที่ยังไม่ได้จับคู่ยังแสดงเป็นงานค้างและกันตรวจทาน/บันทึกตามกฎเดิม ส่วน Preview ยังใช้ตรวจผลและ diagnostics ได้ตามพฤติกรรมเดิม ไม่บังคับให้จับคู่เสร็จทั้งชุดจึงจะปิด modal ได้

## ตัวอย่างข้อมูลและโปรแกรมเดิม

ข้อมูลสมมติ `first_name="EXAMPLE"`, `last_name="SAMPLE"`:

```json
{
  "targetPath": "inform.fullName",
  "value": {
    "kind": "concat",
    "values": [
      { "kind": "source", "field": "first_name" },
      { "kind": "source", "field": "last_name" }
    ],
    "separator": " "
  }
}
```

ตารางหลักแสดง `inform.fullName` ในแถว `first_name` และ `last_name` แต่สร้าง JSON assignment เพียงครั้งเดียว; ถ้าเปลี่ยน expression ผ่านแถวใด อีกแถวต้องแสดงผลเดียวกันหลังยืนยัน

หนึ่งต้นทาง `reference="SYNTHETIC-001"` จับคู่ไป `inform.reference` และ `inform.externalId` → 2 assignments; การเลือกเพิ่มเติมใน modal แล้วยกเลิกต้องไม่เพิ่ม assignment ใดจริง

Array: เพิ่มรายการ 2 ของ `inform.beneficiaries[]` ใน draft และจับคู่ Source `beneficiary_name_2` ไปยัง `inform.beneficiaries[2].name` (เลขบนจอเริ่ม 1 ตามเดิม) พร้อม `notBlank(source.beneficiary_name_2)` → ยืนยันแล้วจึงสร้าง concrete item index 1/emitWhen ใน program รูปเดิม

## ผลหลังผู้ใช้ยืนยัน (2026-11-25, M-45)

- ทำตาราง 4 คอลัมน์ `ข้อมูลต้นทาง | ปลายทางที่จับคู่ | สถานะ | จัดการ` แล้ว โดยไม่แสดงคอลัมน์/ค่าตัวอย่าง; ค้นหาชื่อต้นทาง/ปลายทางและกรองทั้งหมด/ยังไม่ใช้/ต้องแก้ไขได้ พร้อมทางเข้า `ค่าอื่น`, `การจับคู่ที่ต้องแก้ไข` และช่องบังคับที่ยังขาด
- Modal เดียวมีส่วนจับคู่ข้อมูลและส่วนรายการ/เงื่อนไข; เลือก source แล้วจับคู่หลาย target, เปิดแก้ expression ที่ใช้หลาย source, แก้ค่าคงที่/metadata/advanced, เลือกรายการ array และเพิ่ม/ลบ/กำหนดเงื่อนไขได้ภายใน draft เดียว
- ใช้/ยกเลิกทั้ง assignments/counts/item conditions/sourceWhen พร้อมกัน; ยกเลิก/Escape คงค่าจริงและคืน focus, ยืนยันค่าที่เปลี่ยนแล้วล้าง Preview เดิม และรีเซ็ตหน้าตารางเพื่อไม่ค้างหน้าที่ว่างหลังกรอง; ยืนยันค่าเดิมไม่ล้าง Preview
- ใช้ ValueExpressionEditor/PredicateEditor เดิม; สลับ target แล้วสร้าง expression editor instance ใหม่ตาม path เพื่อไม่ค้าง JSON draft ของอีก target; รวม source references จาก case predicates ด้วยและไม่อ่าน literal JSON เป็น expression
- Array ใช้ concrete paths/ลำดับบนจอแบบเดิม; ลบเฉพาะรายการสุดท้ายและข้อมูลลูกของรายการนั้น, ไม่ลบรายการแรกหรือ mapping อื่น, กันอ้างกลุ่มที่ถูกลบ; โปรแกรมยังไม่ส่งรายการที่ไม่มี mapped field และเงื่อนไขยังผูกกับข้อมูลที่ส่งจริงตามกลไก `buildProgram` เดิม
- หลักฐาน: Web `npm run build` ผ่าน; `npm run test:ci` **132/132 ใน 13 suites** (12 tests ใหม่ของ model + 3 tests ใหม่ของ root apply/cancel); `git diff --check` ผ่าน
- Edge headless QA ผ่านด้วยข้อมูลสมมติ: ไม่แสดงตัวอย่าง, source-first headers, หนึ่งต้นทางหลาย target, shared concat, advanced case, literal/metadata, draft/cancel/focus/Escape, array ซ้อน/เงื่อนไขทั้งชุด, ลบ array แล้วยกเลิก, auto-map ใน draft, ซ่อม source ที่ถูกลบ, กันเงื่อนไขผิด, ค้นหาตาม target/กรองยังไม่ใช้ และ 60/40 sticky; ไม่มี runtime exception หรือคำขอเขียน Mapping API
- ผล layout ที่ 1440/1280 × 1000 px: ฝั่งซ้าย/ขวา 3:2, ไม่มี page overflow, Preview top 16 px เมื่อเลื่อน, modal กว้าง 1120 px สูง 801 px และ footer อยู่ใน viewport
- ขอบเขตหลักฐานคือ frontend/โปรแกรมกับข้อมูลสมมติ ไม่ได้รัน Preview API ด้วยไฟล์จริงหรือ external delivery E2E; commit และ push Web `e6349e4` (โค้ด) + `a85f618` (styles) ขึ้น `origin/develop` แล้วตามคำสั่งผู้ใช้ โดยใช้ผล build/tests **132/132** จาก source ชุดเดียวกัน
