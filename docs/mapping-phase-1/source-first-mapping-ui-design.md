# จับคู่จากข้อมูลต้นทางและจัดการใน modal

## คำขอและขอบเขต

ผู้ใช้ 2026-11-25 ขอให้ตารางจับคู่ยึดข้อมูลต้นทางเป็นหลัก เลือก map ไปยังปลายทางผ่าน modal และรวมการจัดการ array; ปรับต่อจาก M-42–M-44 โดยใช้ Transformation Program/contract เดิม ไม่เปลี่ยนกฎธุรกิจหรือ API

## หน้าหลัก

ฝั่งซ้าย 60% ยังคงรายละเอียดปลายทางแบบย่อและส่วนจับคู่ข้อมูล ฝั่งขวาเป็น Preview sticky 40%:

| ข้อมูลต้นทาง | จับคู่ไปยังปลายทาง | สถานะ | จัดการ |
|---|---|---|---|
| reference | inform.reference | จับคู่แล้ว | จัดการ |
| first_name | inform.fullName | จับคู่แล้ว | จัดการ |
| last_name | inform.fullName | จับคู่แล้ว | จัดการ |
| extra_code | — | ยังไม่ใช้ | จับคู่ |

- แต่ละแถวคือ Key ในขั้นที่ 1 ใช้ header เป็นข้อมูลประกอบเมื่อมี; ค้นหาชื่อต้นทาง/ปลายทาง และกรองยังไม่ใช้/ต้องแก้ไขได้; ตามคำขอผู้ใช้เพิ่มเติม ไม่แสดงคอลัมน์หรือค่าตัวอย่างในตารางและ modal จับคู่
- คอลัมน์ปลายทางแสดงได้หลายรายการต่อหนึ่งต้นทาง; หนึ่ง expression ที่ใช้หลายคอลัมน์ปรากฏในทุกแถวที่เกี่ยวข้อง แต่เก็บ assignment เพียงชุดเดียวตาม target path
- ส่วนหัวคงจำนวนช่องบังคับปลายทางที่จับคู่แล้ว และปุ่ม `จัดการการจับคู่` เพื่อเปิด modal ได้แม้ยังไม่มีต้นทางถูกเลือก
- เงื่อนไขเลือกแถวและการ์ด array เดิมย้ายเข้า modal หน้าหลักแสดงเพียงสรุป เช่น `ส่งทุกแถว` / `มีเงื่อนไข` และจำนวนรายการที่ตั้งค่า
- ใต้ตารางมีทางเข้าจัดการ `ค่าอื่น (ค่าคงที่ / ข้อมูลไฟล์)` และ `การจับคู่ที่ต้องแก้ไข` เพื่อไม่ซ่อน expressions ที่ไม่มี Source field หรืออ้างถึง field ที่ลบไป; ไม่สร้าง Source field ปลอมลงโปรแกรม
- Source ที่ยังไม่ใช้ไม่ถือเป็นข้อผิดพลาด เพราะไม่จำเป็นต้องใช้ทุกคอลัมน์; ช่องบังคับของปลายทางยังตรวจเช่นเดิม

## Modal: จัดการการจับคู่

ใช้ modal เดียวมี 2 ส่วนสลับดูได้:

### 1. จับคู่ข้อมูล

- เปิดจากแถว → เลือกข้อมูลต้นทางแถวนั้นไว้ล่วงหน้า พร้อมรายการปลายทางที่ใช้อยู่ โดยไม่แสดงค่าตัวอย่าง
- เลือกปลายทางแบบค้นหาได้ แล้วเลือกว่าจะใช้ค่าตรง ๆ หรือตั้งการแปลงด้วย Value Expression Editor เดิม เช่น trim/แปลงชนิด/ต่อข้อความ
- เพิ่มปลายทางได้หลายช่องสำหรับต้นทางเดียว และแก้ expression ที่ใช้หลายคอลัมน์ได้โดยมีข้อความบอกว่าปลายทางนั้นใช้คอลัมน์ใดร่วมกัน
- ถ้าปลายทางถูกจับคู่แล้ว ให้เปิดค่าเดิมให้แก้ ไม่เขียนทับโดยเงียบ; การนำ assignment ออกหมายถึงนำการจับคู่ของ target path นั้นออกจากฉบับร่าง ไม่ใช่ลบเฉพาะการแสดงในแถวต้นทางใดแถวหนึ่ง
- ตัวเลือก `ค่าอื่น (ค่าคงที่ / ข้อมูลไฟล์)` เปิดแก้ assignment ที่ไม่อ่านต้นทาง รวมถึง advanced expressions เดิม; ต้นทางที่ถูกลบต้องมีรายการเตือนและเปิดแก้ได้
- แสดงช่องบังคับปลายทางที่ยังขาด เพื่อให้เลือกเติมได้โดยไม่ต้องกลับไปใช้ตารางปลายทางเป็นหน้าหลัก
- ปุ่มจับคู่ตามชื่อคอลัมน์อยู่ใน modal และทำกับฉบับร่างเท่านั้น

### 2. รายการและเงื่อนไข

- เลือกแถวที่จะส่งด้วย Predicate Editor เดิม
- เลือกกลุ่ม array ตาม schema แล้วเพิ่ม/ลบรายการ เลือกรายการที่จะตั้งค่า และกำหนดเงื่อนไขส่งแต่ละรายการ
- เมื่อจับคู่ไปยัง array เลือกรายการ เช่น `inform.beneficiaries[1]` ก่อนเลือกช่องปลายทาง และเพิ่มรายการใหม่จากบริบทนั้นได้; สามารถกลับส่วนจับคู่เพื่อตั้ง field ของรายการที่เลือกใน modal เดิม
- กลุ่มซ้อนแสดง path ของ parent และลำดับรายการชัดเจน; ลบรายการสุดท้ายตามพฤติกรรมเดิมและล้างเฉพาะ draft ของรายการ/กลุ่มลูกนั้น ไม่กระทบรายการอื่น
- รายการที่ไม่จับคู่ field ใดจะไม่ถูกส่งตามกลไกเดิม ไม่เพิ่มกฎผู้รับประโยชน์หรือข้อมูลธุรกิจเอง

## การยืนยันและยกเลิก

- เปิด modal แล้วคัดลอก assignments, item counts, item conditions และ sourceWhen เป็นฉบับร่างของหน้าต่างนั้น
- เพิ่ม/แก้/นำ mapping ออก, auto-map, เปลี่ยน array/เงื่อนไข → ยังไม่เปลี่ยนตารางหลักหรือ Preview
- Footer: `ยกเลิก` / `ใช้การตั้งค่านี้`; ใช้สำเร็จแล้วอัปเดต state ทั้งชุดพร้อมกันและล้างผล Preview เก่าที่ไม่ตรงค่าล่าสุด
- ยกเลิก/ปิด/Escape → ทิ้ง draft คง mapping/array/เงื่อนไข/Preview เดิม และคืน focus ให้ปุ่มที่เปิด modal
- ตรวจ target ซ้ำ/target ที่ไม่มีแล้ว/คอลัมน์ที่หายไป/เงื่อนไขผิดใน draft; ช่องบังคับปลายทางที่ยังไม่ได้จับคู่ยังแสดงเป็นงานค้างและกันตรวจทาน/บันทึกตามกฎเดิม ส่วน Preview ยังใช้ตรวจผลและ diagnostics ได้ตามพฤติกรรมเดิม ไม่บังคับให้จับคู่เสร็จทั้งชุดจึงจะปิด modal ได้

## ตัวอย่างข้อมูลและโปรแกรมเดิม

ข้อมูลสมมติ `first_name="EXAMPLE"`, `last_name="SAMPLE"`:

```json
{
  "targetPath": "inform.fullName",
  "value": {
    "kind": "concat",
    "values": [
      { "kind": "source", "field": "first_name" },
      { "kind": "source", "field": "last_name" }
    ],
    "separator": " "
  }
}
```

ตารางหลักแสดง `inform.fullName` ในแถว `first_name` และ `last_name` แต่สร้าง JSON assignment เพียงครั้งเดียว; ถ้าเปลี่ยน expression ผ่านแถวใด อีกแถวต้องแสดงผลเดียวกันหลังยืนยัน

หนึ่งต้นทาง `reference="SYNTHETIC-001"` จับคู่ไป `inform.reference` และ `inform.externalId` → 2 assignments; การเลือกเพิ่มเติมใน modal แล้วยกเลิกต้องไม่เพิ่ม assignment ใดจริง

Array: เพิ่มรายการ 2 ของ `inform.beneficiaries[]` ใน draft และจับคู่ Source `beneficiary_name_2` ไปยัง `inform.beneficiaries[2].name` (เลขบนจอเริ่ม 1 ตามเดิม) พร้อม `notBlank(source.beneficiary_name_2)` → ยืนยันแล้วจึงสร้าง concrete item index 1/emitWhen ใน program รูปเดิม

## แบบปรับเพิ่มเติมตามภาพผู้ใช้ 2026-11-25 — ยืนยันและทำแล้ว (M-46)

ส่วนนี้เป็นแบบปรับจาก M-45 สำหรับหน้าต่างที่เปิดด้วยปุ่ม `จับคู่` / `จัดการ` ของแถวต้นทาง ผลทดสอบของ M-45 ด้านล่างเป็นของ UI รุ่นก่อน ยังไม่ใช่หลักฐานของแบบใหม่นี้

### สรุปพฤติกรรมรุ่นสุดท้ายตามคำยืนยันเพิ่มเติม

- เปิดจากปุ่มของแต่ละแถว: แสดง source ที่หัวและการ์ดปลายทาง ไม่มีแท็บเดิม; หนึ่ง source จับคู่ได้หลายปลายทาง
- array เดียวกันรวมหลาย Index/field ในการ์ดเดียวตาม M-47; ต่างกลุ่ม/concrete parent แยกการ์ด เงื่อนไขส่งยังผูกกับ index ของรายการ
- การ์ด array ไม่มีส่วน `เงื่อนไขการจับคู่` ใต้กรอบ; ปลายทางทั่วไปเปิดส่วนแปลงค่าจาก checkbox ได้
- editor ของ source ที่เลือกไม่ถาม `ค่าจากคอลัมน์` หรือชื่อ field ซ้ำทั้งระดับหลักและ expression ลูก; ใช้ source ของแถวนั้นอัตโนมัติ และคงค่าเดิมที่อ่านคอลัมน์อื่นเป็นข้อความโดยไม่เขียนทับ
- ตัวเลือกปลายทาง/field ไม่มีข้อความต่อท้าย `มีการจับคู่แล้ว`; ใช้ path เดิมเป็นค่าที่เลือก
- หน้าหลักไม่มีปุ่มสรุป `ส่งทุกแถว` และปุ่ม `จัดการการจับคู่` ด้านบนตาราง รวมถึงไม่มีขั้น tour ที่ชี้สองปุ่มนี้; เปิดการ์ดจากปุ่มในแถว และจัดการ array/เงื่อนไขแถวทั้งชุดจากปุ่มรายการ array ที่ยังอยู่
- ส่วนผลระหว่างทางด้านล่างเก็บไว้เป็นประวัติ; การเพิ่มรายการที่เคยสร้างการ์ดแยกและ editor ลูกที่เคยเลือก source ได้ ถูกแทนด้วยพฤติกรรมข้างต้นในรุ่นสุดท้าย

ผล commit/push (2026-11-25): Web **`34414e5`** — `feat(mapping): group array mappings in source destination cards` (โค้ด/tour/tests 8 ไฟล์) และ **`0c2bc9e`** — `style(mapping): style grouped destination mapping cards` (เฉพาะ styles) push ขึ้น `origin/develop` แล้วตามคำสั่งผู้ใช้; source รุ่นสุดท้ายผ่าน `npm run build`, `npm run test:ci` **141/141 ใน 13 suites** และ `git diff --check` โดยไม่มีการแก้ source หลัง checks ก่อน commit

- หัวหน้าต่างแสดง `จัดการการจับคู่` และชื่อต้นทาง เช่น `trn_no`; เอาแท็บ `จับคู่ข้อมูล` และ `รายการและเงื่อนไข` ออกจากหน้าต่างของแถวนั้น
- แสดงการ์ดปลายทางแทนตาราง แต่ละการ์ดมีช่อง `ไปยังปลายทาง` และ checkbox `เพิ่มเงื่อนไขพิเศษ`; ใต้การ์ดมีปุ่มกรอบเส้นประ `+ เพิ่มการจับคู่ข้อมูลปลายทาง` เพื่อเพิ่มอีกการ์ดของต้นทางเดียวกัน
- checkbox เป็นตัวเปิดส่วนตั้งค่าภายในการ์ด ไม่เปิด dialog อีกหน้าต่าง; การจับคู่ตรงยังใช้ค่าจากต้นทางที่เลือก
- ปลายทางทั่วไป: เมื่อติ๊ก แสดงหัวข้อ `เงื่อนไขการจับคู่` และตัวแก้ Value Expression เดิม รองรับ `case` ที่มี expression ลูกซ้อนตามภาพ; โหลด expression เดิมที่มีการแปลงแล้วต้องเปิดให้เห็นโดยไม่แทนที่ด้วยค่าตรง
- ปลายทาง array: แสดงชื่อกลุ่ม เช่น `inform.driver[]` และส่วนรายการที่มี `Index` กับ `field` เช่น `inform.driver[1].trn_no`; เลือกกลุ่ม/field จาก schema ที่ใช้งานจริง ไม่สร้าง field ตามภาพเอง
- แต่ละรายการ array มี checkbox `ส่งเมื่อมีเงื่อนไข`; เมื่อติ๊กแสดง Predicate Editor เดิม กำหนดเงื่อนไขส่งของรายการนั้นตาม `emitWhen` ซึ่งใช้ร่วมกับ field อื่นของรายการเดียวกัน ไม่ใช่เงื่อนไขเฉพาะ field
- Index บนจอเริ่ม 1 ตามเดิม แต่ concrete path ภายในเริ่ม 0; ต้องคงการเพิ่มรายการ/array ซ้อน และไม่ทำ assignment ของรายการอื่นสูญหาย
- ส่วนเลือกแถวที่จะส่งและการจัดการทั้งชุดเข้าจากปุ่มรายการ array บนหน้าหลัก; คง draft/ยืนยัน/ยกเลิกตามเดิม

### ตัวอย่างข้อมูลสมมติ

สมมติ schema ทดสอบมี `inform.trn_no` และ `inform.driver[].trn_no` และต้นทาง `trn_no` มีค่า `SYNTHETIC-001`:

| สิ่งที่เลือกบนจอ | สิ่งที่เก็บใน draft |
|---|---|
| ไปยังปลายทาง `inform.trn_no`, ไม่เพิ่มเงื่อนไขพิเศษ | assignment path `inform.trn_no`, value `{"kind":"source","field":"trn_no"}` |

### ข้อกำหนดเพิ่มเติม: รวมรายการของ array เดียวกันในการ์ดเดียว (2026-11-25 — ยืนยันและทำแล้ว M-47)

ผู้ใช้ขอให้ `เพิ่มรายการ` ของ array เดียวกันอยู่ภายในการ์ดเดิม และแยกการ์ดเฉพาะเมื่อเป็นคนละ array เพื่อไม่ให้สับสน; ส่วนนี้ปรับพฤติกรรมเพิ่มรายการที่เคยสร้างการ์ดใหม่ในผลรุ่นก่อนด้านล่าง

- หนึ่งการ์ดของ array แสดง `ไปยังปลายทาง` ของกลุ่มนั้นเพียงครั้งเดียว; ภายในเป็นรายการย่อยที่มี Index/field และ checkbox ส่งเมื่อมีเงื่อนไขของรายการนั้น
- กด `เพิ่มรายการ` ในการ์ด → เพิ่ม Index ถัดไปและรายการย่อยภายในการ์ดเดิม คง field ที่จับคู่และเงื่อนไขของรายการก่อนหน้า
- คนละกลุ่ม array → คนละการ์ด; ระบุกลุ่มด้วย concrete parent path เพื่อไม่รวม array ลูกที่อยู่คนละ parent item เข้าด้วยกัน
- เปิดข้อมูลเดิมที่มีหลาย assignments ใน array เดียวกัน → รวมแสดงในการ์ดเดียวตั้งแต่เปิดหน้าต่าง โดยไม่รวม/ย้าย index หรือทำ expression เดิมสูญหาย
- ถ้าเพิ่มปลายทางแล้วเลือก array ที่มีการ์ดอยู่แล้ว → รวมรายการไว้ในการ์ดเดิม ไม่สร้างการ์ดซ้ำ; การจับคู่ target path ต้องไม่ซ้ำ
- รองรับหลาย field ที่จับคู่จาก source เดียวกันภายใต้ array/index เดียวกันโดยไม่ตัด assignment ทิ้ง; เงื่อนไขส่งยังผูกกับรายการ/index และใช้ร่วมกับ field ของรายการนั้นตาม `emitWhen` เดิม
- การนำการ์ดออกนำเฉพาะการจับคู่ของ source ที่กำลังแก้ในกลุ่มนั้นออกจาก draft ไม่ล้าง field ที่จับคู่จาก source อื่น; ยืนยัน/ยกเลิกทั้งชุดตาม M-45 และคง Web server ที่ผู้ใช้กำลังใช้งาน
- คงข้อปรับ UI ที่ผู้ใช้ยืนยันก่อนหน้า: array ไม่แสดงส่วน `เงื่อนไขการจับคู่` ใต้กรอบ และไม่เพิ่มช่องเลือก source ซ้ำ

ตัวอย่างสมมติ source `no="SYNTHETIC-001"` และ schema ทดสอบมีสองกลุ่ม:

| การ์ด | รายการย่อยบนจอ | assignment path ภายใน |
|---|---|---|
| `inform.beneficiaries[]` | Index 1 / `inform.beneficiaries[1].seq` | `inform.beneficiaries[0].seq` |
| การ์ดเดิม `inform.beneficiaries[]` | Index 2 / `inform.beneficiaries[2].seq` หลังเพิ่มรายการ | `inform.beneficiaries[1].seq` |
| อีกการ์ด `inform.drivers[]` | Index 1 / `inform.drivers[1].seq` | `inform.drivers[0].seq` |
