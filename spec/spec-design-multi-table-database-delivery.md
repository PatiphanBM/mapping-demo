# Introduction

This specification defines the approved Phase 2 extension for delivering one emitted Transformation output to multiple existing tables in one external PostgreSQL or SQL Server database. It establishes compatibility, mapping, schema, persistence, transaction, reconciliation, security and rollback decisions before implementation begins.

This document is an addendum to [Database Table Destination Design](spec-design-database-table-destination.md). The parent specification remains authoritative for the existing `databaseTable` destination and its persisted jobs. This approved addendum is authoritative for the future `databaseTransaction` destination.

Approval of this document authorizes preparatory design work only. It does not authorize runtime implementation, database migration, production rollout, multi-table activation or Gate I approval.

## 1. Purpose & Scope

### 1.1 Purpose

The future system shall let an authorized user select one server-owned Database Destination Profile and configure an ordered set of existing target tables. Each table operation shall have its own target fields, schema snapshot and duplicate policy. A Source expression may be assigned to fields in more than one operation. The Database Delivery Worker shall execute the complete operation set in one target-local transaction.

### 1.2 Initial Phase 2 scope

- PostgreSQL and SQL Server providers already supported by `databaseTable`.
- Exactly one Database Destination Profile per destination.
- Between 2 and 16 ordered table operations per destination.
- Exactly one parameterized `INSERT` per table operation for each emitted Transformation output.
- Existing target tables only; no target DDL.
- Per-operation field mapping, schema snapshot/hash and duplicate policy.
- One target connection and one all-or-nothing transaction per emitted output.
- Retry and reconciliation from persisted encrypted deterministic values, never from the current Active Config Version.
- Existing Transformation expressions, functions, lookups and metadata bindings.

### 1.3 Out of scope for the initial Phase 2 implementation

- Multiple Database Destination Profiles in one destination.
- Distributed transactions or atomic writes across databases.
- Generic `UPDATE`, `UPSERT`, `DELETE`, `MERGE`, stored procedures or browser-supplied SQL.
- More than one row per operation for one emitted output.
- Operation-level `emitWhen`; an emitted output executes every declared operation.
- Array-to-child-row expansion.
- Reading an identity/default/generated value from one operation and passing it to another operation.
- Automatic compensation after a confirmed commit.
- Automatic conversion of an existing `databaseTable` Config Version or Delivery Job.

## 2. Definitions

- **DatabaseTransaction Destination**: An immutable Destination Definition with kind `databaseTransaction` that selects one Database Destination Profile and an ordered set of Table Operations.
- **Table Operation**: One parameterized `INSERT` into one allowlisted existing target table, identified by a stable `operationKey`.
- **Operation Key**: An immutable logical identifier used as the mapping namespace and persisted operation identity. It is not a schema or table name.
- **Combined Target Schema**: A compiler schema whose root contains one object per Operation Key and whose child fields are writable target columns from that operation's Target Schema Snapshot.
- **Delivery Bundle**: Durable external-delivery intent for one emitted Transformation output and all of its Table Operations.
- **Bundle Identity**: The stable identity `(rowJobId, outputKey)` for the new destination kind.
- **Operation Identity**: The stable identity `(deliveryBundleId, operationKey)` within a bundle.
- **Bundle Payload**: Canonical ordered operation values encrypted and hashed before target I/O.
- **Atomic Delivery**: All operations commit in one target-local transaction or none of the new writes commit.
- **Bundle Reconciliation**: Post-failure comparison of every operation that has an Existing Unique Key to determine the outcome of the complete bundle.
- **Partial Existing State**: A reconciliation result where only some operation rows exist, or where existing rows do not all equal the persisted mapped values.
- **Generated-key Propagation**: Reading a value generated by an earlier operation and assigning it to a later operation. This capability is outside the initial scope.

## 3. Requirements, Constraints & Guidelines

### 3.1 Compatibility requirements

- **COM-001**: The existing `DatabaseTableDestination` CLR model, `kind: "databaseTable"` JSON shape, validation rules, compiler behavior and runtime effects shall remain unchanged.
- **COM-002**: Existing `database_delivery_jobs`, attempts, resolution audit, schema checks, outbox identity and retry semantics shall remain the compatibility path for `databaseTable`.
- **COM-003**: Multi-table behavior shall use a new `kind: "databaseTransaction"` discriminator. The implementation shall not add optional table arrays to `databaseTable`.
- **COM-004**: Historical and Active Config Versions shall never be converted automatically between `databaseTable` and `databaseTransaction`.
- **COM-005**: A user shall create and activate a new Config Version to change destination kind or operation set.
- **COM-006**: `LegacyTable`, `ApiContract`, `JsonFile` and `DatabaseTable` exact JSON/runtime regression shall remain green before the new destination can be enabled.

### 3.2 Destination and operation requirements

- **DST-001**: A `databaseTransaction` destination shall contain one `profileId` and an ordered `operations` collection with 2–16 entries.
- **DST-002**: Every `operationKey` shall match `^[a-z][a-z0-9-]{0,62}$` and shall be unique using ordinal comparison within the destination.
- **DST-003**: Operation order shall be the array order persisted in the immutable Config Version. Retry shall use the persisted order.
- **DST-004**: Every operation shall pin schema, table, write mode, duplicate policy, Target Schema Snapshot and Schema Hash.
- **DST-005**: Every operation profile/provider identity shall match the destination profile. An operation shall not override `profileId`.
- **DST-006**: `writeMode` shall be exactly `insert` in the initial implementation.
- **DST-007**: One emitted Transformation output shall create one Delivery Bundle containing one row insert per declared operation.
- **DST-008**: A filtered or zero-output Transformation result shall create no Delivery Bundle.
- **DST-009**: Multiple Transformation outputs shall create independent bundles using their stable `outputKey`; they shall not share one target transaction.
- **DST-010**: No operation shall be conditionally skipped after an output has been emitted.
- **DST-011**: Each operation shall select a distinct `(schema, table)` target within the destination using the selected provider's identifier-comparison rules.

### 3.3 Mapping and compiler requirements

- **MAP-001**: The Combined Target Schema root shall expose each operation as an object named by `operationKey`.
- **MAP-002**: A target field path shall be `operationKey.columnName`, for example `order.order_number` or `audit.reference_no`.
- **MAP-003**: A Source field or any supported deterministic expression may be assigned to fields in more than one operation.
- **MAP-004**: The compiler shall reject a target path whose operation key or column does not exist in the pinned destination snapshots.
- **MAP-005**: Every writable `NOT NULL` column without a database default shall be assigned for every operation in every emitted output branch.
- **MAP-006**: Every selected Existing Unique Key column shall be assigned deterministically before target execution.
- **MAP-007**: Identity, generated, computed, SQL Server `rowversion`, unsupported and non-writable columns shall not be assignment targets.
- **MAP-008**: Mapping shall reuse the existing `TransformationProgram` and `FieldAssignment.TargetPath` expression vocabulary. The destination shall not duplicate expressions inside its JSON.
- **MAP-009**: Arrays or nested target paths below `operationKey.columnName` shall be rejected in the initial implementation.
- **MAP-010**: The existing maximum of 256 field assignments per Transformation output applies across all operations combined.
- **MAP-011**: A target column that cannot be represented unambiguously by the existing `TargetPath` grammar shall be unavailable for `databaseTransaction` mapping with a safe diagnostic. This restriction shall not change `databaseTable` behavior.

### 3.4 Schema requirements

- **SCH-001**: Every operation shall pin its own immutable Target Schema Snapshot and Schema Hash.
- **SCH-002**: Browse, validate, activate and delivery preflight shall inspect every operation through the existing provider Inspector Module.
- **SCH-003**: A breaking change in any operation shall block the entire bundle before target write begins.
- **SCH-004**: Compatible additions shall not modify the Config Version or add assignments automatically.
- **SCH-005**: Operation validation shall apply the parent specification's required/default/generated/type and Existing Unique Key rules independently to every operation.
- **SCH-006**: Schema diagnostics shall include `operationKey` and safe field-level details without returning raw catalog SQL, connection data or business values.

### 3.5 Persistence and identity requirements

- **PER-001**: The implementation migration shall be expand-only and shall add new bundle/operation persistence for `databaseTransaction`; it shall not repurpose or rewrite existing `database_delivery_jobs` rows.
- **PER-002**: Delivery Bundle identity shall be unique by `(row_job_id, output_key)` within the new destination persistence.
- **PER-003**: Persisted Table Operation identity shall be unique by `(delivery_bundle_id, operation_key)`.
- **PER-004**: Row normalization shall persist the complete encrypted canonical Bundle Payload, bundle hash, exact profile configuration hash, ordered operation metadata and one outbox event in the Mapping PostgreSQL transaction.
- **PER-005**: Safe operation metadata shall include operation key, provider/schema/table, schema snapshot/hash, duplicate policy and mapped column names. Plaintext mapped values shall not be stored outside the encrypted Bundle Payload.
- **PER-006**: The new destination shall use a distinct outbox topic and consumer contract from `mapping.database-delivery`; the current topic/key behavior shall remain unchanged.
- **PER-007**: Retry shall use the exact persisted Bundle Payload, order, profile hash, snapshots, policies and mapped values. It shall not rebuild the bundle from a current config.
- **PER-008**: A duplicate normalization message with identical deterministic bundle hash shall return the existing identity without creating another bundle or outbox event.
- **PER-009**: A duplicate identity with different deterministic bundle content shall fail closed as an invalid row outcome.

### 3.6 Target execution requirements

- **TXN-001**: The Worker shall resolve one profile, open one target connection and begin one target-local transaction for the complete bundle.
- **TXN-002**: Before beginning target writes, the Worker shall verify payload integrity, refresh every target schema, compare every snapshot and prepare every parameterized command.
- **TXN-003**: The Worker shall execute operations sequentially in persisted array order.
- **TXN-004**: The Worker shall commit exactly once after every operation succeeds.
- **TXN-005**: A failure before commit begins shall roll back the target transaction. No operation shall be marked independently delivered.
- **TXN-006**: Values shall use provider parameters and inspected/quoted identifiers. Raw identifier or value interpolation from browser input is prohibited.
- **TXN-007**: Database defaults may supply omitted columns, but a default/identity/generated result shall not feed another operation in the initial implementation.
- **TXN-008**: The Interface presented to `RowNormalizeHandler` shall remain one destination call. Operation orchestration shall remain behind the Destination Module seam.

### 3.7 Bundle status and reconciliation requirements

- **REC-001**: Status shall be bundle-level using the existing vocabulary: `Pending`, `Delivering`, `Delivered`, `AlreadyDelivered`, `RetryableFailed`, `PermanentFailed`, `DeliveryConflict`, `BlockedSchemaDrift` and `UnknownOutcome`.
- **REC-002**: A bundle shall not expose per-operation retry or manual completion.
- **REC-003**: A unique violation or ambiguous commit shall initiate Bundle Reconciliation when every operation has a usable Existing Unique Key.
- **REC-004**: If every operation row exists and every canonical mapped value equals the persisted values, the bundle result shall be `AlreadyDelivered`.
- **REC-005**: If every operation row is absent after an authoritative reconciliation read, the bundle may be retried according to bounded policy.
- **REC-006**: If any existing operation row differs from persisted values, the bundle result shall be `DeliveryConflict` and automatic overwrite shall be prohibited.
- **REC-007**: Partial Existing State shall produce `DeliveryConflict` and shall not be retried automatically.
- **REC-008**: If any operation uses `manualUnknownOutcome`, or if reconciliation is unavailable or cannot prove the complete bundle after a unique violation or ambiguous commit, the bundle shall produce `UnknownOutcome`.
- **REC-009**: `UnknownOutcome` manual actions shall require authorization, operator, reason, correlation ID, duplicate-risk acknowledgement where applicable and append-only audit.
- **REC-010**: A confirmed pre-execution/transient failure shall be retryable without reconciliation when no target command could have executed.

### 3.8 Security and operational requirements

- **SEC-001**: Browser contracts shall contain logical profile/operation identities and safe schema projections only.
- **SEC-002**: SQL text, target host, connection string, credentials and payload values shall not appear in normal logs, metrics, ProblemDetails or audit.
- **SEC-003**: Target credentials shall have catalog read, reconciliation read and `INSERT` permission only for every selected table. DDL permission is prohibited.
- **SEC-004**: Operation keys, schema names, table names and column names shall not be unbounded metric labels.
- **SEC-005**: Creation, activation and delivery gates for `databaseTransaction` shall be independently operable from existing `databaseTable` gates.
- **SEC-006**: Production enablement shall require PostgreSQL and SQL Server atomicity/recovery fixtures, security review, runbook rehearsal, controlled canary and owner approval in a future implementation gate.

### 3.9 Migration, deployment and rollback requirements

- **MIG-001**: Phase 30 preparatory work shall add no migration, discriminator, runtime model, topic or feature gate.
- **MIG-002**: Future implementation shall deploy additive persistence and code support with creation/activation/delivery gates disabled by default.
- **MIG-003**: Mixed deployments shall reject `databaseTransaction` creation and activation until all API and Worker instances understand the new discriminator and persistence contract.
- **MIG-004**: Enabling or disabling the new destination shall not change current `databaseTable` profiles, jobs, controls or delivery consumers.
- **MIG-005**: Rollback before first new-kind use may remove unused additive objects. Rollback after any Config Version or bundle exists shall retain additive data, pause new-kind delivery and reactivate a prior Config Version for new File Jobs only.
- **MIG-006**: Existing pinned bundles shall never be rerouted to `databaseTable` or another destination during rollback.
- **MIG-007**: Destructive removal of new-kind persistence shall require a separate retention/export decision and is not part of automated rollback.

### 3.10 Guidelines

- **GUD-001**: Prefer application-assigned UUID or stable business keys when rows relate across operations.
- **GUD-002**: Keep operation keys stable when cloning/editing a draft so diagnostics, audit and tests remain understandable.
- **GUD-003**: Keep provider dialect, transaction orchestration and reconciliation behind a deep Database Transaction Module with PostgreSQL and SQL Server Adapters.

## 4. Interfaces & Data Contracts

### 4.1 Destination definition

```json
{
  "kind": "databaseTransaction",
  "profileId": "orders-postgres",
  "operations": [
    {
      "operationKey": "order",
      "schema": "public",
      "table": "orders",
      "writeMode": "insert",
      "duplicatePolicy": {
        "kind": "existingUniqueKey",
        "columns": ["order_id"]
      },
      "schemaHash": "sha256:orders...",
      "schemaSnapshot": {}
    },
    {
      "operationKey": "audit",
      "schema": "public",
      "table": "order_audit",
      "writeMode": "insert",
      "duplicatePolicy": {
        "kind": "existingUniqueKey",
        "columns": ["order_id", "event_type"]
      },
      "schemaHash": "sha256:audit...",
      "schemaSnapshot": {}
    }
  ]
}
```

The destination contains target identity and delivery policy only. Transformation expressions remain in `TransformationProgram`.

### 4.2 Mapping contract

```json
{
  "outputKey": "main",
  "fields": [
    {
      "targetPath": "order.order_id",
      "value": { "kind": "source", "field": "OrderId" }
    },
    {
      "targetPath": "audit.order_id",
      "value": { "kind": "source", "field": "OrderId" }
    },
    {
      "targetPath": "audit.event_type",
      "value": { "kind": "literal", "type": "text", "value": "Imported" }
    }
  ]
}
```

The example uses the existing strict `TransformationProgram` and `ValueExpression` JSON property names.

### 4.3 Compiled delivery shape

```csharp
public sealed record DatabaseTransactionPlan(
    string ProfileId,
    string ProfileConfigurationHash,
    IReadOnlyList<DatabaseTableOperationPlan> Operations);

public sealed record DatabaseTableOperationPlan(
    string OperationKey,
    TargetSchemaSnapshot SchemaSnapshot,
    DatabaseDuplicatePolicy DuplicatePolicy,
    IReadOnlyDictionary<string, object?> Values);
```

The public Destination Router seam remains compile/deliver once per row envelope. Provider-specific command text, parameters, transactions, error codes and reconciliation queries remain implementation details.

### 4.4 Persistence identity

```text
Delivery Bundle: UNIQUE(row_job_id, output_key)
Table Operation: UNIQUE(delivery_bundle_id, operation_key)
Outbox:          one unsent event per Delivery Bundle
Attempt:         one ordered attempt sequence per Delivery Bundle
```

## 5. Acceptance Criteria

- **AC-COM-01**: Given any historical `databaseTable` Config Version, when the addendum implementation is deployed, then exact JSON, compilation, job identity, payload hash, outbox and retry effects remain unchanged.
- **AC-COM-02**: Given a `databaseTransaction` JSON document, when an old or gated-off instance receives it, then creation/activation is rejected rather than interpreted as `databaseTable`.
- **AC-DST-01**: Given operations from different profiles, when validation runs, then the destination is rejected before Config Version creation.
- **AC-DST-02**: Given duplicate/invalid operation keys or duplicate target tables, when validation runs, then diagnostics identify each operation path.
- **AC-MAP-01**: Given one Source field mapped to two operation target paths, when transformation evaluates, then both operation values contain the same deterministic Source value.
- **AC-MAP-02**: Given an unmapped required field in any operation, when compilation runs, then the entire Config Version is invalid.
- **AC-MAP-03**: Given an identity/generated field or nested/array target path, when compilation runs, then the assignment is rejected.
- **AC-MAP-04**: Given a target column that is ambiguous in the existing TargetPath grammar, when the table is inspected for the new destination, then that column is unavailable with a safe diagnostic and current `databaseTable` behavior is unchanged.
- **AC-SCH-01**: Given breaking drift in one table and healthy schemas in all others, when delivery preflight runs, then no target transaction begins and the bundle is `BlockedSchemaDrift`.
- **AC-PER-01**: Given one emitted output, when Mapping PostgreSQL commits normalization, then exactly one encrypted Delivery Bundle, its ordered operation metadata and one outbox event commit atomically.
- **AC-PER-02**: Given the same bundle identity and same canonical content, when persistence repeats, then no duplicate bundle/event is created; different content fails closed.
- **AC-TXN-01**: Given three valid operations, when delivery succeeds, then all three rows become visible after one target commit.
- **AC-TXN-02**: Given operation two fails before commit, when rollback completes, then no new row from operations one, two or three is visible.
- **AC-TXN-03**: Given a database-generated identity in operation one is referenced by operation two, when validation runs, then the initial implementation rejects the dependency.
- **AC-REC-01**: Given an ambiguous commit and every operation row exists with equal values, when reconciliation completes, then the bundle is `AlreadyDelivered`.
- **AC-REC-02**: Given an ambiguous commit and every keyed operation row is absent after authoritative reads, when reconciliation completes, then bounded retry may proceed.
- **AC-REC-03**: Given any differing row or Partial Existing State, when reconciliation completes, then the bundle is `DeliveryConflict` and no automatic overwrite/retry occurs.
- **AC-REC-04**: Given an ambiguous commit and any operation lacks a usable unique key, when recovery runs, then the bundle is `UnknownOutcome` and automatic retry stops.
- **AC-SEC-01**: Given any request, response, log, metric, diagnostic or audit path, when inspected, then it contains no connection value, raw SQL or plaintext mapped values.
- **AC-MIG-01**: Given the preparatory Phase 30 change set, when diff is inspected, then it contains no migration, new discriminator, runtime code, topic or feature gate.
- **AC-ROLL-01**: Given new-kind jobs exist and rollback is invoked, when new delivery is paused, then jobs retain their pinned destination/data and are not rerouted to `databaseTable`.

## 6. Test Automation Strategy

- **Contract**: exact `databaseTable` golden serialization remains unchanged; strict new-kind JSON accepts only the approved fields and rejects unknown members.
- **Compiler**: Combined Target Schema, operation-key paths, cross-operation Source reuse, required/key coverage, field limits and generated/nested/array rejection.
- **Mapping PostgreSQL integration**: additive migration idempotence, bundle/operation uniqueness, encrypted canonical payload, hash conflict, outbox atomicity, lease and append-only audit.
- **PostgreSQL target integration**: three-table commit, second-operation rollback, unique reconciliation, schema drift and ambiguous-commit recovery.
- **SQL Server target integration**: equivalent transaction, parameter, error-classification and reconciliation behavior using an explicit required fixture.
- **Crash recovery**: before connection, before first command, between commands, before commit acknowledgement and after commit acknowledgement.
- **End-to-end**: select one profile, add multiple tables, map one Source value to different fields, activate, normalize, deliver and inspect bundle-level status.
- **Security**: identifier injection, profile/schema allowlist bypass, raw SQL/value redaction, unauthorized resolution and unsafe retry.
- **Regression**: all existing destination, immutable-version, reprocess, schema monitor and delivery operations suites.

Tests shall exercise the same deep Module Interface used by production callers. Provider databases remain real system boundaries for provider integration tests.

## 7. Rationale & Context

Changing the existing `databaseTable` contract from one table to an array would couple historical Config Versions, job identity, persistence, retry and rollout to the new feature. A new destination kind preserves a stable compatibility path and permits independent feature gates and rollback.

Namespacing target fields by `operationKey` reuses the existing typed Transformation Program. The compiler can present multiple table schemas as one Combined Target Schema, while the destination retains ownership of target identity and delivery policy. Callers still make one destination call; provider and transaction complexity stays behind a deep Module.

One profile is required because one PostgreSQL or SQL Server connection can provide an atomic local transaction. Multiple profiles would require distributed transactions or compensation and are therefore a separate capability.

Pre-known keys make operation ordering, retries and reconciliation deterministic. Generated-key propagation would add provider-specific value capture and new dependency semantics, so it is intentionally deferred.

## 8. Dependencies & External Integrations

### External Systems

- **EXT-001**: Existing PostgreSQL target database containing every selected table.
- **EXT-002**: Existing SQL Server target database containing every selected table.

### Infrastructure Dependencies

- **INF-001**: Mapping PostgreSQL for immutable Config Versions, additive bundle persistence, attempts, audit and outbox.
- **INF-002**: Kafka for the future bundle-identity delivery event.
- **INF-003**: Existing server-owned Database Destination Profiles and secret configuration.

### Data Dependencies

- **DAT-001**: Canonical Target Schema Snapshots for every operation.
- **DAT-002**: Stable Transformation `outputKey`, `operationKey` and deterministic mapped values.

### Technology Platform Dependencies

- **PLT-001**: Existing Transformation, Destination Router, Target Schema Inspector and database provider Adapters.
- **PLT-002**: PostgreSQL and SQL Server drivers capable of local transactions and typed parameters.

### Compliance Dependencies

- **COM-DEP-001**: Target data classification must permit reconciliation reads for every operation using an Existing Unique Key.
- **COM-DEP-002**: Existing payload encryption, retention, audit and secret-redaction policies apply to the complete bundle.

## 9. Examples & Edge Cases

### 9.1 One value written to multiple tables

```text
Source.OrderNo = "ORD-001"

order.order_number       <- Source.OrderNo
audit.reference_no       <- Source.OrderNo
summary.source_order_no  <- Source.OrderNo
```

All three assignments are evaluated deterministically before the bundle is persisted.

### 9.2 Operation failure rolls back earlier inserts

```text
BEGIN
  order   INSERT succeeds
  audit   INSERT fails FK/check constraint
  summary not executed
ROLLBACK

Result: no new order/audit/summary row; classify the bundle failure
```

### 9.3 Ambiguous commit with complete reconciliation

```text
Commit acknowledgement is lost.
order, audit and summary rows all exist and equal persisted values.
Result: AlreadyDelivered
```

### 9.4 Partial existing state

```text
order row exists and equals persisted values.
audit row is missing.
summary row exists with different values.
Result: DeliveryConflict; no automatic retry or overwrite
```

### 9.5 Operation without a unique key

```text
All inserts were sent; commit acknowledgement is lost.
audit uses manualUnknownOutcome.
Result: UnknownOutcome; authorized manual resolution required
```

### 9.6 Generated parent key dependency

```text
orders.id is identity-generated.
order_items.order_id requests orders.id from the prior operation.
Result: Config Version validation failure in the initial implementation
```

### 9.7 Cross-profile selection

```text
order  -> orders-postgres
audit  -> audit-sqlserver
Result: destination validation failure before activation
```

## 10. Validation Criteria

- Every requirement group traces to testable acceptance criteria.
- `databaseTable` exact JSON and runtime characterization remain authoritative and unchanged.
- The design defines operation identity, per-operation schema/key policy, mapping namespace, order, atomicity, reconciliation and ambiguous outcomes without permissive defaults.
- The initial scope explicitly excludes cross-profile transactions, multi-row operations and generated-key propagation.
- The migration strategy is additive and leaves existing jobs and topics untouched.
- Rollback never reroutes a pinned bundle or rewrites a historical Config Version.
- Phase 30 Step 30.0 changes only documentation and targeted regression evidence.
- Mapping, Platform/Operations, Security and Target Database owners approve the decisions before Step 30.1 begins.
