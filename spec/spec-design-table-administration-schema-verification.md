# Introduction

This specification defines Phase 28 Table Administration and physical PostgreSQL schema verification. It extends the existing typed Table Module without changing runtime mapping semantics or immutable Config Version behavior.

## 1. Purpose & Scope

Authorized operators can create Source or Normalized tables, inspect metadata, add one column at a time, view configuration impact and compare authoritative metadata with the physical schema through `/admin/tables`.

In scope: expand-only create/add-column, read-only verification, safe field diagnostics, usage projection, authorization, audit, rate limiting, observability and a mutation kill switch.

Out of scope: drop, rename, alter type/length/nullability, truncate, hard delete, arbitrary SQL, automatic drift repair and business-row query/preview/export.

## 2. Definitions

- **Authoritative metadata**: `table_definitions` and `table_columns`.
- **Physical schema**: PostgreSQL columns, types, nullability, identity, primary key and unique constraints.
- **System column**: Column generated by `DdlBuilder` for Source or Normalized runtime semantics.
- **Business column**: Typed column stored in `table_columns`.
- **Inspector Module**: Deep module whose interface accepts a server-resolved table identity/definition and returns a typed verification result.
- **Adapter**: PostgreSQL implementation that reads `pg_catalog` with parameterized queries.
- **Drift**: Any expected/actual structural difference. Drift is never repaired automatically.
- **Gate H**: Owner approval required before production Table Admin mutations are enabled.

## 3. Requirements, Constraints & Guidelines

### Ownership and physical schema

- **TBL-001**: `table_definitions` and `table_columns` shall be authoritative; the browser shall never submit schema name, connection data or SQL.
- **TBL-002**: Source expected system columns are `id`, `file_job_id`, `row_number`, `physical_line_number`, `imported_at`; unique key is `(file_job_id,row_number)`.
- **TBL-003**: Normalized expected system columns are `id`, `source_row_id`, `output_key`, `file_job_id`, `row_number`, `row_job_id`, `config_version_id`, `normalized_at`; unique key is `(source_row_id,output_key)`.
- **TBL-004**: `id` shall be a bigint identity primary key. System nullability and all supported business type metadata shall match `DdlBuilder` output.
- **TBL-005**: Business database columns remain nullable even when mapping metadata has `isRequired=true`.

### Verification

- **VER-001**: Status lifecycle is `Unknown → Verifying → Healthy|Drifted|Missing|VerificationFailed`.
- **VER-002**: Inspector shall compare column presence/order-independent identity, canonical PostgreSQL type, length/precision/scale, nullability, identity, primary key and unique constraints.
- **VER-003**: Type aliases shall canonicalize before comparison (`int4→integer`, `int8→bigint`, `varchar(n)→character varying(n)`, `timestamptz→timestamp with time zone`).
- **VER-004**: `Missing` means the resolved physical relation does not exist. Catalog permission, timeout or availability failure maps to `VerificationFailed`.
- **VER-005**: Diagnostics may contain structural field path/code/expected/actual values only; no query text, connection data, server path, stack trace or row value.
- **VER-006**: Verification is read-only. It shall not execute DDL or update authoritative column metadata.
- **VER-007**: Latest status/check time is persisted for list views; append-only verification history stores safe snapshots without list-time catalog N+1 queries.

### Mutation, authorization and audit

- **AUT-001**: Permissions are `TableAdmin.Read`, `TableAdmin.Create` and `TableAdmin.AddColumn`.
- **AUT-002**: Create/add-column require actor, reason and correlation ID; production mutations additionally require `TableAdministration:MutationsEnabled=true`.
- **AUT-003**: Read/detail/verify remain available when mutations are disabled.
- **AUD-001**: Successful create/add-column audit commits in the metadata/DDL transaction. Rejected conflicts append a safe failure audit when persistence is available.
- **MUT-001**: Create and add-column reuse `TableDefinitionValidator`, `DdlBuilder` and existing transactions.
- **MUT-002**: Add-column locks the table metadata row before assigning the next ordinal. Physical/metadata mutation is atomic.
- **MUT-003**: Add-column resets latest status to `Unknown`; UI verifies again after success.
- **MUT-004**: v1 exposes no destructive or type-changing operation.

### Usage, limits and operations

- **IMP-001**: Detail shall project Mapping Config, historical Config Version, active marker and pinned File Job count without mutating any reference.
- **LIM-001**: List pagination is bounded to 1–100 items. Verification allows 12 requests per table per minute and catalog commands time out after five seconds.
- **OBS-001**: Metrics use bounded action/status/result labels, never table/column/operator/reason labels.
- **OBS-002**: Alerts cover repeated catalog failure, detected Drifted/Missing state and unauthorized mutation.
- **CON-001**: No new third-party package is required.
- **CON-002**: Production `MutationsEnabled` remains false after Gate H approval until a separate controlled rollout change.
- **GUD-001**: Drift recovery follows impact analysis, backup and the runbook; default action is pause and investigate, never repair.

## 4. Interfaces & Data Contracts

```csharp
public interface ITableSchemaInspector
{
    Task<TableSchemaVerificationResult> InspectAsync(
        long tableId,
        TableDefinition expectedDefinition,
        CancellationToken cancellationToken = default);
}
```

The interface hides PostgreSQL catalog queries and comparison rules. The controller resolves the typed definition from table ID before calling it.

| Endpoint | Permission | Behavior |
|---|---|---|
| `GET /tables` | Read | bounded metadata list/search/filter using persisted status |
| `GET /tables/{id}` | Read | metadata detail |
| `POST /tables` | Create + gate | transactional metadata/DDL/audit; returns ID |
| `POST /tables/{id}/columns` | AddColumn + gate | one additive transactional column |
| `GET /tables/{id}/verification` | Read | latest persisted result |
| `POST /tables/{id}/verify` | Read + rate limit | fresh read-only catalog comparison |
| `GET /tables/{id}/references` | Read | safe Config/Version/pinned-job impact |

## 5. Acceptance Criteria

- **AC-TBL-HEALTH-01**: Given valid Source/Normalized metadata and DDL, when verified, then status is Healthy with no diagnostics.
- **AC-TBL-DRIFT-01**: Given extra, missing or type/nullability/identity-changed column, when verified, then status is Drifted with field-level safe diagnostics.
- **AC-TBL-DRIFT-02**: Given primary/unique constraint drift, when verified, then status is Drifted and identifies only structural constraint columns.
- **AC-TBL-MISSING-01**: Given missing physical table, when verified, then status is Missing without auto-create.
- **AC-TBL-FAIL-01**: Given catalog outage/permission/timeout, when verified, then status is VerificationFailed without infrastructure details.
- **AC-TBL-CREATE-01**: Given a valid form, when created, then metadata/DDL/audit commit once, response is 201 with ID, UI redirects and verifies.
- **AC-TBL-ADD-01**: Given concurrent additive requests, when committed, then row locking produces unique ordered metadata and physical columns without changing existing columns.
- **AC-TBL-AUTH-01**: Given missing/wrong permission or disabled gate, mutation is rejected without DDL.
- **AC-TBL-IMPACT-01**: Given active/historical references and pinned jobs, detail displays impact without rewriting them.
- **AC-TBL-SEC-01**: OpenAPI/UI contain no raw SQL, schema/connection field or data browser operation.

## 6. Test Automation Strategy

- Unit: type aliases, expected schemas, validator reuse, authorization, kill switch, rate limit and safe metrics.
- PostgreSQL integration: healthy Source/Normalized, extra/missing/type/constraint drift, missing relation, parameterized identifier, latest history/audit and concurrent add-column.
- End-to-end: create→redirect→Healthy, add-column→Healthy, drift diagnostics and mutation-hidden kill switch.
- Regression: all LegacyTable, ApiContract, JsonFile, retry/reprocess, Profile and Contract suites.
- Frameworks: existing xUnit, Dapper/Npgsql and Playwright; no package addition.

## 7. Rationale & Context

Metadata persistence proves intended structure, not current physical structure. A deep Inspector Module localizes PostgreSQL vocabulary and comparison rules so controllers and UI cannot construct catalog queries or infer DDL. Persisted latest status makes list cost bounded while explicit verify keeps inspection operator-controlled.

## 8. Dependencies & External Integrations

### External Systems

- **EXT-001**: PostgreSQL catalog supplies physical structure.

### Infrastructure Dependencies

- **INF-001**: Existing migration runner applies verification/audit schema.
- **INF-002**: Existing identity layer supplies permission claims in production.

### Data Dependencies

- **DAT-001**: Mapping Config/Version/File Job references provide impact projection.

### Technology Platform Dependencies

- **PLT-001**: Existing .NET 8/Npgsql/Dapper and Next.js/Playwright stack.

### Compliance Dependencies

- **COM-001**: Control plane shall not disclose business rows or credentials.

## 9. Examples & Edge Cases

```text
Expected: columns.amount = numeric(18,2), nullable
Actual:   columns.amount = integer, nullable
Result:   Drifted / ColumnTypeMismatch

Expected relation absent:
Result:   Missing / TableMissing (no CREATE or repair)

Catalog unavailable:
Result:   VerificationFailed / CatalogUnavailable (no host/query text)
```

## 10. Validation Criteria

- Migration, backend PostgreSQL-required suite, formatter, TypeScript, lint, production build and Playwright pass.
- Production npm and NuGet vulnerability scans have no vulnerable runtime package.
- Operations runbook, acceptance matrix and Gate H evidence are complete.
- Platform/Operations, Security and Mapping owners explicitly approve Gate H before production mutation enablement.
